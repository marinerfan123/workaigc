## 1. SSE 实现机制

### 1.1 传输方式

- **传输协议：SSE（Server-Sent Events）**，基于 `GET /api/generate/stream`，`Content-Type: text/event-stream; charset=utf-8`。
- 不涉及 WebSocket；也不是长轮询（long-polling）。前端 `EventSource` 单例常驻连接。
- 关键响应头（`server.js:2597-2602`）：
  - `Cache-Control: no-cache, no-transform`
  - `Connection: keep-alive`
  - `X-Accel-Buffering: no`（主动关闭反代缓冲，避免事件被攒批）
- 首行下发 `retry: 3000\n\n`（`server.js:2603`），指导浏览器断线后 3s 自动重连。

**证据**：【源码已证实】`server.js:2595-2614`（SSE 端点）、`realtime.cjs:38,57`（数据帧 `data: ...\n\n` 格式）。置信度 **HIGH**。

### 1.2 事件总线实现（是否进程内 EventEmitter）

- **是纯进程内 `EventEmitter`**（Node.js `events` 模块），**无任何跨进程/跨重启持久化**。
  - `realtime.cjs:11-13`：`const { EventEmitter } = require('events'); const emitter = new EventEmitter();`
  - `realtime.cjs:14`：`emitter.setMaxListeners(0);`（解除 Node 默认 10 监听器上限，避免 `MaxListenersExceededWarning`）
  - 事件键命名空间：`u:${userId}`（`realtime.cjs:23,32`）。
- **连接注册表**：`conns = new Map()`，`userId -> Set(res)`（`realtime.cjs:17`），按用户隔离，防多用户串看（对应 G1 安全项）。
- 推送入口 `emitTaskUpdate(userId, payload)` 仅做 `emitter.emit('u:'+userId, payload)`，且 **try/catch 包裹、best-effort、绝不阻断主流程**（`realtime.cjs:20-27`）。
- 源码注释自承：`realtime.cjs:9`「纯内存单进程通道，不做跨进程/跨重启持久化」。

**证据**：【源码已证实】`realtime.cjs:11-49`。置信度 **HIGH**。

### 1.3 连接数限制

- **无显式连接数上限**。`conns` Map 随活跃连接增长，`setMaxListeners(0)` 已解除监听器告警上限，但 `conns` 本身无 `max` 阈值。
- 每个浏览器标签页持有 **1 个全局 `EventSource`**（`useGenerationStream.ts:24,32` 模块级单例 `es`），但单进程内同一用户多标签/多设备连接数无上限保护。
- 风险：【推断】高并发在线用户下，单进程内存中 `conns` 与监听器持续累积，缺少驱逐/限流，存在 OOM 与事件风暴放大风险。置信度 **LOW**（需压测确认）。

**证据**：【源码已证实】`realtime.cjs:17,30-49`、无阈值代码；【未知·待核验】实际上限表现。

### 1.4 心跳 / 超时

- **服务端心跳**：每 **20s** 向连接写入注释帧 `: ping\n\n`（`server.js:2611`），仅用于保活、防止代理/中间件因空闲断开长连接，**不携带业务数据**。
- **连接清理**：`res.on('close')` 时 `clearInterval(hb)` 并调用 `unsub()` 反注册（`server.js:2612`）；`unsub` 会 `emitter.off` + 从 `conns` 删除，set 空则删 userId（`realtime.cjs:44-48`）。
- **无服务端写超时**：SSE 连接本身没有「空闲多少秒强制断开」的服务端超时逻辑，依赖心跳保活 + 客户端/代理层超时。
- 前端侧：客户端原生 `EventSource` 自动重连，受服务端 `retry: 3000` 指引。

**证据**：【源码已证实】`server.js:2610-2613`、`realtime.cjs:44-48`。置信度 **HIGH**。

### 1.5 客户端重连逻辑

- **依赖原生 `EventSource` 自动重连**：服务端下发 `retry: 3000`，断线后浏览器约 3s 重连（`server.js:2603`）。
- 前端 `es.onopen` 复位 `esDisabled = false`；`es.onerror` 将 `es = null` 且 `esDisabled = true`（`useGenerationStream.ts:33-49`）。
- ⚠️ **潜在缺陷（次级）**：`es.onerror` 把 `esDisabled` 置 `true` 后，若底层 `EventSource` 原生重连触发 `onopen`，会把 `esDisabled` 复位为 `false`，而模块变量 `es` 仍为 `null`；此后任意 `waitForTask` 调用 `ensureConnection()` 会**新建第二个 `EventSource`**，导致重复连接/重复事件投递。该路径属 `EventSource` 自动重连与原生语义的交互细节。
  - **证据**：【源码已证实】`useGenerationStream.ts:29-53`；实际是否触发重复连接【未知·待核验】。置信度 **MEDIUM**。

**证据**：【源码已证实】`useGenerationStream.ts:29-53`、`server.js:2603`。置信度 **HIGH**。

### 1.6 服务端如何推送任务状态变更

- 任务终态切换由 `dispatcher` 在多处调用 `realtime.emitTaskUpdate(user_id, { taskId, status, error })`（`dispatcher.cjs:674,720,921,956,1254` 等），覆盖 `done / failed / canceled` 等终态。
- 推送 payload 形状与轮询 `getTaskStatus` 同源同构（`realtime.cjs:51-82` 的快照回灌对齐 `getTaskStatus` 字段），便于前端无差别处理。
- **连接建立即回灌在途快照**：`server.js:2606-2609` 调用 `realtime.snapshotActive(pgPool, userId)`，查询 `status IN ('running','waiting') OR completed_at > now-1h`（上限 200 条），逐条 `data: ...\n\n` 下发，解决「刷新/连接前漏事件」。
- 取消推送示例：`dispatcher.cjs:1252-1254` 的 `cancelTask` 标记 `canceled` 并 `realtime.emitTaskUpdate(row.user_id, { taskId, status: 'canceled', error: '用户已取消' })`。

**证据**：【源码已证实】`dispatcher.cjs:674,720,921,956,1254`、`realtime.cjs:53-82`、`server.js:2606-2609`。置信度 **HIGH**。

## 2. 轮询兜底

- **机制**：`waitForTask(taskId, { timeoutMs })` 在监听 SSE 的同时，每 **3s** 调用 `apiGetGenerationStatus(taskId)`（`useGenerationStream.ts:88-97`）。
- **触发条件**：
  - SSE 未连（`esDisabled` / `EventSource` 不可用）时，仅靠轮询（连接建立也会回灌快照，但实时性降级）。
  - SSE 连接正常时仍并行轮询——即「SSE 近实时 + 3s 轮询双保险」，任一命中终态即 `resolve`。
  - 设计意图明确（注释 `useGenerationStream.ts:1-6`）：生成「完成判定」是核心关键路径，对 SSE 故障零信任依赖。
- **终态判定**：`done / failed / cancelled / not_found` 任一即 `settle`（`useGenerationStream.ts:84,92`）。
- **超时兜底**：超过 `timeoutMs`（视频默认 95min、图片 3.5min，`GenerationBar.tsx:520-521`）仍非终态 → `settle(last)`，保留 pending 显示「生成中」，绝不误判失败（`useGenerationStream.ts:93`、`GenerationBar.tsx:579-581`）。
- **轮询接口**：`GET /api/generate/status/:taskId` → `dispatcher.getTaskStatus` 直读 `generation_tasks` 表 `status` 字段原值返回（`server.js:2577-2581`、`dispatcher.cjs:1019-1046`）。

**证据**：【源码已证实】`useGenerationStream.ts:60-100`、`server.js:2576-2582`、`dispatcher.cjs:1019-1046`、`GenerationBar.tsx:519-582`。置信度 **HIGH**。

## 3. 已知 Bug（重点）

### 3.1 ⛔ 取消状态拼写不一致：`canceled`（单 l，服务端）vs `cancelled`（双 l，前端）—— 取消语义失效

> ⚠️ 任务简报描述的方向有偏差：简报称「前端 `canceled`（双 l）/ 服务端 `canceled`（单 l）」，但**实际代码方向相反**。下文以源码为准修正。

**服务端（权威）使用 `canceled`（单 l，美式）**：
- `cancelTask` 落库：`updateTaskStatus(pgPool, taskId, 'canceled', ...)`（`dispatcher.cjs:1252`）
- 取消推送 SSE：`realtime.emitTaskUpdate(row.user_id, { taskId, status: 'canceled', ... })`（`dispatcher.cjs:1254`）
- poll 循环返回：`status: 'canceled'`（`dispatcher.cjs:275,284,716,953` 等）
- 状态接口 `getTaskStatus` 直接返回 DB 原值 `row.status`（`dispatcher.cjs:1031`）→ **轮询兜底也返回 `canceled`（单 l）**
- 注释亦自相矛盾：`WorkspacePage.tsx:393` 注释写 `SSE canceled`（单 l），`WorkspacePage.tsx:409` 注释写 `SSE 推送 cancelled`（双 l）。

**前端（消费方）使用 `cancelled`（双 l，英式）**：
- 类型定义：`status: ... | 'cancelled' | ...`（`useGenerationStream.ts:11`）
- `waitForTask` 终态匹配：`u.status === 'cancelled'`（`useGenerationStream.ts:84`）、`st.status === 'cancelled'`（`useGenerationStream.ts:92`）
- 消费分支：`if (final.status === 'cancelled')`（`GenerationBar.tsx:570`）

**失效链路（已端到端串证）**：
1. 用户取消 → 服务端标记 DB `canceled`、推 SSE `{status:'canceled'}`。
2. 前端 `onUpdate` 收到 SSE 帧，`last = u`，但 `'canceled' !== 'cancelled'`，**`settle` 不被调用**（`useGenerationStream.ts:82-85`）。
3. 3s 轮询拿到 `getTaskStatus` 返回的 `canceled`（单 l），同样 `'canceled' !== 'cancelled'`，**`settle` 不被调用**（`useGenerationStream.ts:92`）。
4. `waitForTask` 仅在 `Date.now() > deadline` 时以 `last`（status=`canceled`）`settle`（`useGenerationStream.ts:93`）。
5. 回到 `pollTaskUntilDone`：`final.status === 'cancelled'`（双 l）为 `false`，`done/failed/not_found` 均不匹配 → **落入「安全线未达终态」分支，保留 pending「生成中」**（`GenerationBar.tsx:579-581`）。
6. `onRemoteCancel`（负责跨标签/远端取消兜底移除幽灵卡片）**永远不会被调用**（`GenerationBar.tsx:575` 仅在 `cancelled` 分支内）。

**实际影响**：
- **同一标签页取消**：`WorkspacePage.handleCancel` 已乐观移除卡片（`WorkspacePage.tsx:394`），用户无感；但 `waitForTask` Promise 仍挂起至超时（资源占用，3.5min/95min）。
- **跨标签页 / 远端取消（P0）**：被取消方所在标签页的 pending 卡片**永久显示「生成中」，直至页面刷新**；SSE 推送虽已到达却被静默忽略，无自动清理路径。
  - 佐证：注释 `WorkspacePage.tsx:409-419` 明确期望「后端 SSE 推送 cancelled → 兜底移除幽灵卡片」，但因 casing 不匹配该路径实际失效。

**修复建议**：统一为单一拼写（推荐前端对齐后端 `canceled` 单 l），或在 `waitForTask` 与 `getTaskStatus` 间做状态归一化（canonicalize）。属「隐藏契约」类缺陷，应加单测锁定 `'canceled'` 字符串常量。

**证据**：【源码已证实】`dispatcher.cjs:1252,1254,275,284,716,953`、`dispatcher.cjs:1031`、`useGenerationStream.ts:11,84,92`、`GenerationBar.tsx:570`、`WorkspacePage.tsx:393,409`。置信度 **HIGH**（P0）。

### 3.2 隐藏契约：状态字符串枚举前后端不一致（不只取消）

- 前端 `TaskUpdate.status` 枚举：`'running' | 'waiting' | 'done' | 'failed' | 'cancelled' | 'not_found' | 'unknown'`（`useGenerationStream.ts:11`）。
- 后端实际产出（DB/接口原值）：`running / waiting / done / failed / canceled（单 l）/ not_found / unknown`。
- 比对结果：**仅 `canceled/cancelled` 一项 casing 不一致**，其余枚举对齐。
- 但前端 `data/media.ts:20` 媒体状态类型用 `'cancelled'`（双 l），与生成通道共用该拼写——说明「取消」在代码库内**没有统一常量**，是散落字符串字面量，极易再次回归。
- `error` 文案（如 `'用户已取消'`）前端未做字符串匹配，仅依赖 `status`，故错误文案不影响逻辑，但属于非结构化「隐藏契约」。

**证据**：【源码已证实】`useGenerationStream.ts:11`、`dispatcher.cjs:1031`、`src/data/media.ts:20`、`realtime.cjs` 推送字面量。置信度 **HIGH**。

### 3.3 次级缺陷：SSE 错误后置 `esDisabled` 可能触发重复连接

见 §1.5 末。原生 `EventSource` 自动重连 + `es=null/esDisabled` 状态机交互，可能在一次瞬时错误后新建第二个 `EventSource`，造成重复事件投递（因 `settle` 幂等，功能不崩，但有冗余连接与监听器）。

**证据**：【源码已证实】`useGenerationStream.ts:29-53`；是否真实触发【未知·待核验】。置信度 **MEDIUM**。

## 4. 多实例 / 水平扩展硬限制

- **结论：纯进程内事件总线，事件不跨实例。** 部署多个后端进程时，实时性（SSE 推送）只在「处理该任务的那个进程」内有效，其它进程的 SSE 连接收不到该任务的状态变更。
- `realtime.cjs` **完全不使用 Redis / 任何跨进程机制**：全文件无 `redis`/`pub/sub`/`ioredis` 引用，仅依赖内存 `EventEmitter`（`realtime.cjs:1-85` 通读）。
- 项目中 Redis **确实存在且启用**（`db.cjs:23`、`redis.cjs`、运行日志 `server.log:5`「🔴 Redis:up」【运行时已证实】），但**仅用于限流（`ratelimit.cjs`）、缓存、日志总线（`logbus.cjs`）**，**未用于生成任务实时事件分发**。
- 官方文档已记载该限制：`docs/deployment-plan.md` 及 `dispatcher.cjs:41` 注释「多实例横向扩展需把 ACCT 状态迁至 Redis（deployment-plan.md §6）」——说明该硬限制为**已知待办**，非本次新发现。
- 影响面：
  - 多副本（PM2 cluster / 容器多实例 / 负载均衡）下，SSE 推送可能「丢事件」给非属主进程的连接；虽有「连接即回灌快照 + 3s 轮询兜底」可最终收敛到正确终态（完成判定不依赖 SSE），但**实时性体验在多实例下退化为轮询级延迟**。
  - 取消推送同样受限于属主进程，跨实例用户连接收不到即时 cancel 推送（结合 §3.1 的 casing bug，跨实例取消几乎必然表现为「幽灵 pending 直到轮询/刷新」）。

**证据**：【源码已证实】`realtime.cjs`（通读无跨进程代码）、`db.cjs:23`、`redis.cjs`、`dispatcher.cjs:41`；【文档记载但源码未证实】`docs/deployment-plan.md §6`（Redis 迁移计划未在当前 `realtime.cjs` 落地）；【运行时已证实】`server.log:5`「Redis:up」。置信度 **HIGH**。

## 6. 审计发现摘要（最关键风险）

1. **【P0】取消状态拼写不一致导致跨标签/远端取消失效**：后端 `canceled`（单 l）与前端 `cancelled`（双 l）不匹配，`waitForTask` 与 `GenerationBar.tsx:570` 均无法命中，被取消方标签页的 pending 卡片永久显示「生成中」直至刷新。证据：【源码已证实】置信度 HIGH。修复：统一常量 + 加单测锁定。

2. **【P1】多实例水平扩展硬限制**：`realtime.cjs` 为纯进程内 `EventEmitter`，事件不跨实例；即便 Redis 已启用也未用于实时分发。多副本部署下 SSE 实时性退化为轮询级，且跨实例取消推送丢失。证据：【源码已证实】+ `docs/deployment-plan.md` 记载。置信度 HIGH。

3. **【P1】隐藏契约脆弱**：生成状态字符串散落为字面量，前后端无共享枚举/常量（仅 `canceled/cancelled` 一项已暴露），任何状态新增/改名都易静默失效。证据：【源码已证实】。置信度 HIGH。

4. **【P2】无连接数上限 + 潜在重复连接**：`conns` Map 无阈值、`setMaxListeners(0)` 解除告警；SSE 错误后 `esDisabled` 状态机可能与原生重连交互产生重复 `EventSource`。证据：【源码已证实】，重复连接是否触发【未知·待核验】。置信度 MEDIUM。

5. **【P2】SSE 异常后从此标签页失活**：`es.onerror` 一旦置 `esDisabled=true`，本页后续 `waitForTask` 不再建连（依赖轮询兜底），实时推送在该标签页会话内永久降级，直至刷新。证据：【源码已证实】。置信度 MEDIUM。
