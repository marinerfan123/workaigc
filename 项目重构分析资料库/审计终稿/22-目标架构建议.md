## 1. 已定架构方向（必须纳入目标态）

以下为产品/技术负责人已定调、本次审计确认无冲突、必须纳入目标架构的硬方向【文档记载+源码已证实·HIGH】：

1. **异步生成全量主流化**：轮询/成败判定/链接落地全收归后端；前端只「提交 + 拿三态」（参照 Replicate/fal.ai/Stability）。
2. **成败只看生成端终态**：固定时间（90min）仅作防僵尸安全线；超时**绝不判失败、绝不退积分**（标 `waiting` 保留）。
3. **浏览器永不持有 `provider.apiKey`**：凭据仅服务端使用。
4. **任务必须 PG 持久化 + 幂等键**：崩溃可捞回（现状已满足，需强化）。
5. **成功即存 OSS**：业务服务器零二进制。
6. **并发 Semaphore**：生成并发信号量（GLOBAL_MAX 可配置）。
7. **前端 SSE + 乐观 UI + 语义状态**：实时采用 SSE 而非 WebSocket。
8. **后台自建生态 · 模块注册表驱动**：`registerModule` 统一分发，L0 平台基座 / L1 供给侧 / L2 需求侧 / L3 人与钱。
9. **技术栈硬约束（不可违反）**：PG17 唯一数据源、Redis7 仅缓存、OSS 阿里云零二进制、**后端 Node 原生 HTTP 中央 handler 分发**（详见 §4 注释——「中央分发」保留，但单体巨函数须拆为注册式 router 表）。

## 2. 目标分层架构

> 依赖方向：**自上向下单向**（接入层→业务域→核心引擎→基础设施），禁止反向依赖与跨层穿透。基础设施层（PG/Redis/OSS/Provider）不得被业务域之外的层直接调用。

```
┌──────────────────────────────────────────────────────────────┐
│ 接入层 (Edge / Gateway)                                       │
│  - 唯一 HTTP 入口：Node 原生 http.createServer               │
│  - 中央分发器 RouterTable（注册式，替代单体 handleAPI 巨函数）│
│  - 统一鉴权中间件 appGateway（会话 cookie 优先，system 令牌   │
│    仅限显式内部 channel）                                      │
│  - 统一错误契约中间件（结构化 ErrorEnvelope）                 │
│  - CORS / 限流 / 请求日志（OpenTelemetry 埋点）               │
└───────────────┬──────────────────────────────────────────────┘
                │ 仅经 RouterTable 注册的路由
┌───────────────▼──────────────────────────────────────────────┐
│ 业务域 (Business Domains)                                     │
│  L2 需求侧：Generation(生成) / Media(作品) / Characters /      │
│            Studio / Shop(市集) / ReferenceStyles / Skills      │
│  L3 人与钱：Auth / Users / Billing(计费) / Accounting(账务) / │
│            Payments(支付) / Finance(对账) / Admin(运营)        │
│  L1 供给侧：ProviderRegistry / ModelHub / OSS / Agent         │
│  L0 平台基座：Setup / Health / Config / ModuleRegistry         │
│  每个域 = 一个注册到 RouterTable 的 handler 模块               │
└───────────────┬──────────────────────────────────────────────┘
                │ 调用
┌───────────────▼──────────────────────────────────────────────┐
│ 核心引擎 (Core Engines)                                       │
│  - AsyncGenerationEngine：提交/调度/轮询/终态/崩溃恢复        │
│    （统一状态机 + 状态枚举常量，消除 canceled/cancelled 类 bug）│
│  - BillingEngine：双余额 reserve/commit/release（事务化+唯一约束）│
│  - AccountingEngine：双边记账（唯一幂等键）                   │
│  - PaymentEngine：下单/验签/幂等入账（复用而非裸 SQL）        │
│  - RealtimeEngine：SSE 发布 + Redis pub/sub 订阅（多实例安全） │
│  - ConcurrencySemaphore（Redis 令牌桶，多实例一致）           │
└───────────────┬──────────────────────────────────────────────┘
                │ 仅经 Repository/DAL
┌───────────────▼──────────────────────────────────────────────┐
│ 基础设施 (Infrastructure)                                     │
│  PG17（唯一数据源，单一 schema 源 + 迁移脚本）                │
│  Redis7（仅缓存/协调：限流、pub/sub、令牌桶、SSE 中继）       │
│  OSS（阿里云，零二进制，成功即存）                            │
│  Provider 适配层（apiKey 仅服务端，加密落库）                 │
└──────────────────────────────────────────────────────────────┘
```

**证据等级**：【文档记载+源码已证实】HIGH。分层边界中的「前端只提交+拿三态」「PG 唯一源」「Redis 仅缓存」均已在 `05-Redis契约`、`04-数据库真实结构`、`06-任务调度状态机` 中得到源码/运行时证实。

## 3. 模块边界与依赖方向

### 3.1 当前问题（目标态需消除）
- 现状：`server.js` 单体 `handleAPI`（约 L1573–3607，>1000 行）内联了鉴权、路由分支、业务调用、错误拼装；`billing`/`accounting`/`payments`/`dispatcher`/`realtime` 为独立模块但调用关系靠命名约定（`idempotencyKey`）而非类型契约耦合【源码已证实·HIGH】。
- 跨层穿透：`webhook.cjs` 直接裸 SQL 写 `users.recharge_credits`（绕过 `BillingEngine`），导致两套记账语义漂移【源码已证实·HIGH，见 08 §7】。
- 后台：`admin.cjs` 巨型 `handleAdmin` switch（约 40+ 分支），与 `finance.cjs`/`shop.cjs`/`reference-styles.cjs` 分散并存【源码已证实·HIGH】。

### 3.2 目标模块边界
| 模块 | 职责边界 | 依赖方向 | 证据 |
|---|---|---|---|
| RouterTable（接入层） | 仅做：解析路由→分发→统一错误/鉴权；不含业务 | ← 业务域 handler 注册 | 【推断】HIGH |
| 业务域 handler | 仅编排：参数校验、调用核心引擎、组装响应 | → 核心引擎 | 【推断】HIGH |
| 核心引擎 | 纯逻辑：状态机/计费/账务/支付/实时；不直接读 `req` | → Repository/DAL | 【推断】HIGH |
| Repository/DAL | 唯一 SQL 出口；所有写操作经事务；强制唯一约束 | → PG | 【推断】HIGH |
| 基础设施 | 不感知业务语义 | 被 DAL/引擎调用 | 【源码已证实】HIGH |

**依赖铁律**：业务域禁止直接写 SQL；所有 `users` 余额变更必须经 `BillingEngine`；所有记账必须经 `AccountingEngine`；`webhook` 入账必须复用 `BillingEngine` 而非裸 SQL。
**证据等级**：【源码已证实】HIGH（当前违规事实）+【推断】HIGH（目标边界）；置信度 HIGH。

### 3.3 后台模块注册表（L0–L3）
- 现状：`admin.cjs` 用 `if/else` 路由分支，扩展性差，与外围 `finance`/`shop` 割裂【源码已证实·HIGH】。
- 目标：引入 `registerModule({ id, layer, routes, permissions })`，按层聚合：
  - **L0 平台基座**：Setup / Health / Config / ModuleRegistry 自身。
  - **L1 供给侧**：ProviderRegistry / ModelHub / OSS / Agent。
  - **L2 需求侧**：Generation / Media / Characters / Studio / Shop / ReferenceStyles / Skills。
  - **L3 人与钱**：Auth / Users / Billing / Accounting / Payments / Finance / Admin 运营。
- `registerModule` 统一分发到接入层 RouterTable，权限声明内聚于模块而非散落 `requireAdmin` 调用点。
**证据等级**：【文档记载但源码未证实】HIGH（方向已定调）；当前 admin 割裂问题为【源码已证实】HIGH。

## 4. API 设计原则

### 4.1 中央分发 vs router
- **保留**：Node 原生 HTTP 中央入口（技术栈硬约束），即 `http.createServer` 单入口 + 统一 `appGateway` 鉴权 + 统一错误契约中间件【硬约束·HIGH】。
- **变革**：以**注册式 RouterTable** 替代单体 `handleAPI` 巨函数。每个业务域 handler 在启动时 `registerRoute(method, path, handler, {auth, scope})`，中央分发器查表路由。这既满足「Node 原生 HTTP 中央 handler 分发」的硬约束（入口与鉴权仍中央），又消除单文件 >1000 行的维护灾难与隐藏契约【推断·HIGH】。
**证据等级**：【源码已证实】HIGH（现状巨函数）+【文档记载】HIGH（硬约束）；置信度 HIGH。

### 4.2 鉴权统一
- 移除 `/api/token` 公开返回（见 §7）；`appGateway` 改为 **cookie 会话优先**，Bearer `system` 令牌仅用于明确的内部服务间 channel（如运维脚本），不暴露给浏览器、不经由前端 `ensureApi()` 下发【源码已证实·HIGH，见 10 §4 P0-A】。
- 统一 `requireScope(role, resource, action)` 取代散落的 `requireAdmin` + 手动 owner 校验；owner 校验由 DAL 强制（SQL `WHERE user_id=$1`）而非 handler 旁路【源码已证实·HIGH，见 03 §3.3/§3.4 IDOR 类缺口】。
**证据等级**：【源码已证实】HIGH；置信度 HIGH。

### 4.3 统一错误契约（详见 §5.2）
- 后端统一返回 `{ ok, code, message, data? }`；`code` 为受控枚举（`NEED_RECHARGE`/`INSUFFICIENT`/`NO_REASONING_MODEL`/`ALREADY_INITIALIZED` 等），HTTP 状态与 `code` 一一对应。
- 前端禁止用 `includes('409')`/`/402|积分不足/` 文本嗅探，改为解析 `code` 枚举【源码已证实·HIGH，见 12 C1/C2/C3】。
**证据等级**：【源码已证实】HIGH；置信度 HIGH。

### 5.2 SNAKE_MAP 替代方案
- **推荐方案**：引入 `@shared` 共享契约层（前后端共用 TypeScript 类型 + 字段别名表），由 DB 迁移脚本生成字段映射并在 CI 中校验「每个 snake_case 列都在契约表中」；或基于 `information_schema.columns` 动态构建映射，消除手工白名单。
- **过渡方案**：保留 `SNAKE_MAP` 但将其提升为**唯一契约源**，并加单测锁定「新增 DB 列必须出现在映射表」，前端用共享枚举消费。
- **禁止**：新增 DB 列仅靠人工同步到 `SNAKE_MAP` 与前端 `data/*.ts`（当前模式，已证实易错）。
**证据等级**：【源码已证实】HIGH（缺口事实）+【推断】HIGH（方案）；置信度 HIGH。

### 5.3 统一错误契约与状态枚举
- 状态枚举（`running/waiting/done/failed/canceled`）收敛为 `@shared` 单一常量 `TASK_STATUS`，前后端共用，加单测锁定字符串【源码已证实·HIGH + 推断·HIGH】。
- 错误体结构化：`{ok:false, code, message}`；`code` 枚举化，CI 校验前后端 code 一致【源码已证实·HIGH】。
**证据等级**：【源码已证实】HIGH；置信度 HIGH。

## 6. 账户/计费目标态（双余额 + 事务/唯一约束）

### 6.1 现状致命缺口
- `credit_transactions(ref,kind)` 仅非唯一索引，commit/release 为 SELECT→INSERT 两步非原子 → TOCTOU 双退/双记【源码已证实·HIGH，07 §6 / 15 P0-1】。
- `consumption_ledger(idempotency_key)` 仅非唯一索引 → 并发双记账、margin 虚高【源码已证实·HIGH，07 §6 / 15 P0-2】。
- 失败键复用时只删 `generation_tasks` 行、不清理 `credit_transactions` → 永久漏退【源码已证实·HIGH，07 §6.1】。
- `webhook` 裸 SQL 入账绕过 `BillingEngine` → 两套语义漂移【源码已证实·HIGH，08 §7】。
- `findDanglingReserves` 死代码（0 调用）与超时阈值 30/90/180min 三套冲突【源码已证实·HIGH，07 §6.4】。

### 6.2 目标态
- **双余额不变**：`reward_credits` + `recharge_credits` 两真实池；`users.credits` 为 `GENERATED ALWAYS` 总计列（已证实，不可写）【数据库已证实·HIGH】。
- **强约束**：`credit_transactions` 加 `(ref, kind)` **唯一约束**，`consumption_ledger` 加 `idempotency_key` **唯一约束**，写入一律 `INSERT ... ON CONFLICT DO NOTHING`【推断·HIGH】。
- **事务化**：`reserve/commit/release` 以及「余额变更 + 流水 + 账务」包进真实 `BEGIN/COMMIT`；`webhook` 入账复用 `BillingEngine`，删除裸 SQL【源码已证实·HIGH + 推断·HIGH】。
- **失败键复用**：复用同一 `idempotency_key` 经 `ON CONFLICT` 自然幂等，杜绝漏退【推断·HIGH】。
- **阈值统一**：单一超时语义（90min 安全线，`waiting` 不退积分），删除冲突死代码【源码已证实·HIGH】。
**证据等级**：【源码已证实】HIGH（缺口）+【推断】HIGH（方案）；置信度 HIGH。

## 8. 实时目标态（支持多实例）

### 8.1 现状硬限制
- `realtime.cjs` 为纯进程内 `EventEmitter`，**事件不跨实例**；多副本下 SSE 实时性退化为轮询级，跨实例取消推送丢失【源码已证实·HIGH，11 §4】。
- 结合 `canceled/cancelled` casing bug，跨实例取消几乎必然表现为「幽灵 pending 直到刷新」【源码已证实·HIGH】。

### 8.2 目标态（Redis pub/sub 或等价）
- **RealtimeEngine**：SSE 连接仍由属主进程维护（连接注册表），但状态变更经 **Redis pub/sub**（`channel: task:{userId}`）广播，所有实例订阅并转发给本进程的连接。
- 保留「连接即回灌快照 + 3s 轮询兜底」双保险（不可移除，现状已证实零信任 SSE 的工程取舍）【源码已证实·HIGH，12 C5】。
- 取消信号同样经 Redis 广播，消除跨实例幽灵 pending【推断·HIGH】。
- 并发令牌桶/等待区状态迁 Redis（与 05 §6 已知待办一致），使多实例 RPM/限流一致【源码已证实·HIGH】。
**证据等级**：【源码已证实】HIGH（现状）+【推断】HIGH（方案）；置信度 HIGH。

## 9. 目标架构验收锚点（衔接 04_重构等价需求基线）

目标架构必须**保留**以下已证实业务行为（不可因重构丢失）：
- 双余额三段式与优先序（F2/F12）【源码已证实·HIGH】。
- 90min 安全线超时 `waiting`、绝不判失败、绝不退积分（F7）【源码已证实·HIGH】。

## 10. 结论
