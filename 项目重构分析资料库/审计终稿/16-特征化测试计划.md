# 16 · 特征化测试计划（Characterization Test Plan）

> 审计对象：墨灵 AI（`E:\code`）
> 文档性质：**只读体检产物**。本计划**不执行任何写入/变更命令**；给出重构前需落地的字符化测试方案。所有证据以既有事实文档（15/21 + 02/03/06/07/08/10/11/12）为基准。
> 用途：在重构前冻结"系统当前**实际**行为"（不是"正确"行为），作为回归安全网。与 17 号文档（Golden Master）互补：本计划锁**行为**，17 锁**输出快照**。
> 证据等级图例：【源码已证实】/【配置文件已证实】/【推断】/【未知·待核验】
> 置信度图例：HIGH / MEDIUM / LOW / UNKNOWN

---

## 1. 目标（必须牢记：冻结"实然"，不验证"应然"）

字符化测试（Characterization Test）的核心目标——**Michael Feathers 定义**——是"描述系统**当前实际**行为，使其在被修改时不至于静默改变"。因此对墨灵 AI 而言：

1. **锁定行为，而非断言正确**：每条用例断言的是"代码**现在**会产出什么"，即使该产出是 bug（如 L-12 T1 空转、L-03 双退）。重构者改动这些代码时，测试会**红**，迫使其**显式决策**（保留/修复/记为破坏性变更），而不是"顺手改掉不知会"。
2. **作为重构安全网**：当前 `npm test` 因框架错配（L-37）实际空跑，本计划的首要交付是"让安全网**真的存在**"。
3. **覆盖生命线**：资金幂等/双退、越权、任务状态机、SSE 字段契约、错误契约、T1 failover 空转为 P0；权限矩阵、支付 webhook、SNAKE_MAP 字段为 P1。
4. **零生产副作用**：所有用例在**内存 PG / 实录快照 / mock provider** 下运行，绝不连生产库、绝不调真实支付/provider、绝不写任何生产数据（见 §6 禁止事项）。

> ⚠️ **关键原则**：若某行为已被认定为缺陷（如 L-22 token 泄露、L-12 空转），字符化测试的"当前预期输出"应**录制缺陷现状**，并在用例注释中标注 `KNOWN_DEFECT / INTENTIONAL_BREAKING_CHANGE 候选`。重构修复该缺陷时，此用例应被**有意更新**（红色→绿色），更新动作本身即"破坏性变更已决策"的证据。

## 3. 用例清单

> 字段说明：**用例ID / 被测行为(来源 Legacy) / 输入 / 当前预期输出（实然） / 断言方式 / 框架**。

### 3.1 计费幂等 / 资金（P0）

**CT-03 · `credit_transactions` 并发双 release 双退**
- 被测行为：L-03
- 输入：并发 2 笔同 `ref`+`kind='release'` 的 `releaseCredits`（同 task，cost=100）
- 当前预期输出（实然）：**两笔均通过 `_hasPosted` 检查 → 余额被加 2 次（200）**；`credit_transactions` 出现 2 行同 `(ref,kind)`。⚠️ KNOWN_DEFECT（无唯一约束，TOCTOU）。
- 断言方式：断言 `users.recharge_credits`（或对应池）增量 == 200（**锁定双退现状**）；断言 `credit_transactions` 该 `(ref,kind)` 行数 == 2。
- 框架：vitest + 内存 PG（`pg-mem` 或临时 schema）+ 并发 `Promise.all`。
- 证据：【源码已证实】HIGH（billing.cjs:48-55/72，server.js:248）。

**CT-04 · `consumption_ledger` 并发双记账**
- 被测行为：L-04
- 输入：并发 2 笔同 `idempotencyKey` 的 `recordConsumption`
- 当前预期输出（实然）：**两笔均插入** → `consumption_ledger` 2 行同键；`margin_cents` 被记 2 次。⚠️ KNOWN_DEFECT（幂等键非唯一）。
- 断言方式：断言该 `idempotency_key` 行数 == 2；断言 `SUM(margin_cents)` 翻倍。
- 框架：vitest + 内存 PG。
- 证据：【源码已证实】HIGH（accounting.cjs:62-68，server.js:656）。

**CT-05 · 失败键复用漏退**
- 被测行为：L-05
- 输入：① `failed` 任务 → `releaseCredits`；② 删 `generation_tasks` 行（不清理 `credit_transactions`，复刻 server.js:2415-2418）；③ 同 key 再次 `failed` → `releaseCredits`
- 当前预期输出（实然）：第二次 `releaseCredits._hasPosted` 命中第一次残留 release 行 → **返回 true，跳过释放** → 用户永久损失 `cost` 积分。⚠️ KNOWN_DEFECT。
- 断言方式：断言最终用户余额 == 初始（未退）；断言 `credit_transactions` 仅 1 行 release。
- 框架：vitest + 内存 PG。
- 证据：【源码已证实】HIGH（server.js:2415-2418，billing.cjs:70-72）。

**CT-02 · 三阶段计费顺序与无事务**
- 被测行为：L-02
- 输入：`reserve`(cost=100) → 模拟进程崩溃（不 commit）→ 重跑同 key `reserve`
- 当前预期输出（实然）：`reserve` 靠 `UPDATE ... WHERE col>=$1` 行级原子；重跑时若首笔 held 未回滚则 `col>=$1` 判断可能失败（暴露无事务窗口）。录制"reserve 仅条件更新、无跨语句事务"现状。
- 断言方式：断言 `users` 对应池在 reserve 后净减 == cost；断言 `generation_tasks` 唯一索引 `ux_gt_idem` 拦第二笔 INSERT（或触发 release 回退，净零）。
- 框架：vitest + 内存 PG。
- 证据：【源码已证实】HIGH（billing.cjs:32-38，07 §4）。

**CT-07 · `balance_after` 取总计列**
- 被测行为：L-07
- 输入：`commitCredits`（charge 仅 recharge 池）
- 当前预期输出（实然）：`credit_transactions.balance_after` == `users.credits`（STORED 总计，含 reward+recharge），**不反映仅 recharge 扣减**的分池值。
- 断言方式：断言 `balance_after == reward_credits + recharge_credits`（当前口径），与分池扣减额不一致时标注口径差异。
- 框架：vitest + 内存 PG。
- 证据：【源码已证实】HIGH（billing.cjs:63）。

**CT-11 · 账/余额分离（单边写入）**
- 被测行为：L-11
- 输入：`commitCredits` 成功（写 `credit_transactions`）但 `recordConsumption` 抛错（模拟）
- 当前预期输出（实然）：`billing` 不写 ledger、`accounting` 不碰余额，二者独立 → 余额已扣但 ledger 缺失，无交叉报错。
- 断言方式：断言余额已减、ledger 无对应行（录制"无交叉校验"现状）。
- 框架：vitest + 内存 PG + 注入 accounting 抛错。
- 证据：【源码已证实】HIGH（accounting.cjs:98-108，07 §6-6）。

**CT-14 · `waiting` 永久 held（超时不退）**
- 被测行为：L-13/L-14
- 输入：任务标记 `waiting`（超时 90min 安全线后）
- 当前预期输出（实然）：`cost` 积分**永久 held**，`scanStuckTasks` 看门狗（仅回收 running>3h）**不碰 waiting** → 余额不变、积分不释放直至人工复核。
- 断言方式：断言用户余额 == 初始 - cost（held 未退）；断言 waiting 任务在 watchdog tick 后仍 held。
- 框架：vitest + 内存 PG + 调用 `scanStuckTasks`。
- 证据：【源码已证实】HIGH（dispatcher.cjs:728-731/982-1001，06 §6）。

### 3.2 任务状态机（P0）

**CT-13 · 超时铁律：timeout→waiting 且余额不变**
- 被测行为：L-13
- 输入：运行任务触发"超时"（mock 90min 安全线）

**CT-15 · 非法状态跃迁不重复 commit/release**
- 被测行为：L-15
- 输入：`success(done)` 后再收到 `success(done)`；`failed` 后再 `running`
- 当前预期输出（实然）：`commitCredits`/`releaseCredits` 经 `_hasPosted` 去重 → 第二次同 `(ref,kind)` **跳过**（但因 L-03 无唯一约束，仅应用层去重）；状态机不阻止 DB 层重复 UPDATE，依赖去重函数。
- 断言方式：断言 `credit_transactions` 对同 `(ref,'commit')` 仅 1 行（或按 L-03 现状 2 行，须与 CT-03 口径一致）；断言状态可被重复写但计费不双计。
- 框架：vitest + 内存 PG。
- 证据：【源码已证实】HIGH（dispatcher.cjs 多处 UPDATE，billing.cjs:60/72）。

**CT-16 · `pending_ids` 仅回传、取消不回滚媒体**

- 断言方式：断言 cancel 后 `media` 表仍有 pending_ids 对应行；断言 `status=='canceled'`。

### 3.3 T1 failover 空转（P0）

**CT-12 · MiniMax/Volcano 返 `'error'` 被当瞬态切账号**
- 被测行为：L-12
- 输入：provider A(minimax) 明确失败返 `status:'error'`；provider B 亦失败
- 当前预期输出（实然）：`attemptOnAccount` 把 `'error'` 当非 success → `markReject + return null` → 切下一账号新建真实 provider 任务；若全失败 → `throttled` → 入 `waiting` → **积分永不释放、任务永不标 failed**。⚠️ KNOWN_DEFECT。
- 断言方式：断言 minimax 被调用 2 次（首次 + failover 新建）；断言最终 `status=='waiting'`（非 failed）；断言用户余额未退（held）。
- 框架：vitest + mock provider 适配器（返回 `{status:'error'}`）+ 内存 PG。
- 证据：【源码已证实】HIGH（minimax.cjs:85，volcano.cjs:121，dispatcher.cjs:450-509/218，06 §10）。

## 4. 框架建议（统一 vitest，修复 L-37）

### 4.1 当前错配（必须修复）
- **事实**：`package.json:13` `"test": "vitest run"`，但 8 个测试文件全用 `node:test`，无 vitest 配置（`vite.config.ts` 无 `test` 块，无 `vitest.config.*`）。`vitest` 不识别 node:test 注册器 → `npm test` **空跑/0 通过**（见 L-37，15 §2）。
- **结论**：重构前必须二选一：
  - **方案 A（推荐）**：统一为 **vitest**。将 node:test 用例迁移为 `import { describe, it, expect } from 'vitest'`；在 `vite.config.ts` 加 `test: { environment, include, globals }` 或新建 `vitest.config.ts`；保留 `package.json` 的 `test: vitest run`（或改为 `vitest` 以 watch 模式）。
  - **方案 B**：保留 node:test，把 `package.json` 改为 `node --test`（与文件头注释一致）。
- **推荐 A**：vitest 与前端 Vite 生态一致、支持 mock/快照/并发、便于后续组件测试；且本计划全部用例以 vitest 书写。

### 4.2 最小可运行脚手架（只读、零生产副作用）
```
project/
├─ vitest.config.ts            # 声明 test 环境（node / jsdom）
├─ tests/
│  ├─ setup/
│  │  ├─ pg-mem.ts            # 内存 PG：用 pg-mem 或临时 schema，不连生产
│  │  ├─ mock-provider.ts     # 假 provider 适配器，返 {status:'error'|'failed'|'success'}
│  │  └─ mock-res.ts          # 捕获 res.write（SSE 帧）
│  ├─ billing.characterization.test.ts   # CT-02~07,11,14
│  ├─ dispatcher.statemachine.test.ts     # CT-12,13,15,16
│  ├─ realtime.contract.test.ts           # CT-17,18,19,20
│  ├─ error.contract.test.ts              # CT-27,28
│  ├─ authz.integration.test.ts           # CT-21~26（本地实例/内存）
│  ├─ payments.webhook.test.ts            # CT-09,10,36
│  ├─ snake-map.test.ts                   # CT-29,06
│  └─ snapshots/                          # Golden Master 基线（见 17）
└─ package.json  (test: vitest run)
```
- **内存 PG**：优先 `pg-mem`（纯 JS 模拟 PG，支持 GENERATED ALWAYS/唯一索引/事务），零外部依赖、零生产副作用；若需更逼真，用测试容器临时库（**仅限本地**，绝不指向 `E:\code` 生产库）。
- **Mock provider**：所有生成类用例用 mock 适配器，断言"重试/切换/failover"行为，不发起真实 HTTP。
- **实录快照**：对生产**只读**导出数据做基线（见 17 §2），测试仅比对快照，不写生产。
- **前端用例**：用 `vitest` + `jsdom` 环境跑 `api.ts`/`useGenerationStream`/`GenerationBar` 逻辑（mock `fetch`/`EventSource`）。

### 4.3 运行约束（写入 CI 注释）
- 所有用例**默认 `environment: 'node'`**（后端）/ `jsdom`（前端逻辑）。
- 数据库用例强制 `pg-mem`，并在用例头断言 `DATABASE_URL` 未指向生产（防御性 guard）。
- 集成测试（authz）仅对**本地临时实例**运行，禁止 `baseURL` 指向生产域名。

## 5. 禁止事项（红线）

1. **禁止断言"应然"**：只断言"实然"。即使用例录制的是 bug（CT-03 双退、CT-12 空转、CT-21 token 泄露），也**必须录制现状**；修复时**有意更新**用例并标注破坏性变更，而非悄悄改期望。
2. **禁止调用真实支付**：所有支付用例用 mock provider + webhook 验签本地模拟（CT-09/10/36），绝不发起真实 easypay 回调。
3. **禁止调用真实 provider**：生成类用例（CT-12/13）用 mock 适配器返回 `{status:'error'|'failed'|'success'}`，不消耗真实 quota/计费。
4. **禁止写生产数据**：数据库用例一律 `pg-mem`/临时 schema；实录基线仅**只读导出**（见 17 §2），测试只读不写。
5. **禁止依赖 `E:\code` 生产库**：用例不引用生产连接串；CI 环境变量 guard 拦截。
6. **禁止把 KNOWN_DEFECT 当"通过"掩盖**：缺陷现状用例须以注释/标签（`@known-defect`）显式标记，纳入"待重构决策"清单，不与正常用例混同。
7. **禁止移除轮询兜底断言（CT-20）**：该行为是设计铁律，字符化测试须永久保留"3s 轮询兜底"断言。
