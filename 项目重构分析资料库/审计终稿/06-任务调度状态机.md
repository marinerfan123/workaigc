# 06 · 任务调度状态机（墨灵AI 重构前体检）

> 证据等级：【源码已证实】——全部来自 `server/dispatcher.cjs`（1358 行）+ `server/providers/video/{index,shared,minimax,volcano,agnes}.cjs` 实读，行号已逐一核对。

## 1. 一次业务请求的完整链路（生成）
```
用户提交 POST /api/generate (server.js:2394)
  → 限流(2396) → 校验 realUser(2405) → 幂等键(2408)
  → 同键历史任务处理(failed 释放旧 held 重生成 / running|done 复用)(2411-2426)
  → modelHubResolver.resolveModelIdentity(2430) → 查 models 计费维度(2437)
  → billing.resolvePayment(2446, 不足返 402) → billing.reserveCredits(2459, 预扣 held)
  → dispatcher.generateAsync(2522)  [sync 模式走 generate(2494)]
        ↓ (异步 fire-and-forget)
  generateAsync(648): INSERT generation_tasks status='running' + cost/cost_pool/idempotency_key(661-663)
        ↓ 立即 fire-and-forget .then(673)
  generate(549): 组装 (model×provider) pairs(579-585) → dispatchOne(529)
        ↓ dispatchOne: round-robin pairs + 令牌桶/并发门控(529-546)
  attemptOnAccount(450): 查 isCold/bucket.tokens/conc → 调 videoGenerate/imageGenerate(464-466)
        ↓ 成功 → persistProviderTaskId 落 provider_task_id+resume_meta(779)
        ↓ 失败/超时/取消 → 见下
  pollLoop(shared.cjs:187): 自适应轮询密度(前1min基线→>15min 60s 封顶)
        ↓ 成功 → finalizeTask: commitCredits(691) + accounting.recordConsumption(699) + 落 media/result + 标 done(710,941)
        ↓ 失败 → releaseCredits(734) + 标 failed(738)
        ↓ 超时(90min安全线) → 标 waiting(728-731) 【绝不判失败、绝不退积分】
        ↓ 取消 → cancelTask(1221): 释放 held + 标 canceled + SSE(1240-1252)
```

## 2. 真实存在的状态（以库 `generation_tasks.status` 为准）
**【源码已证实】库状态仅 5 个**（grep 全文确认 `queued`/`processing` 零出现）：
| 状态 | 设置位置 | 触发 | 终态? |
|---|---|---|---|
| `running` | INSERT 默认(662)；入等待区保持(719) | 任务被接受 | 否 |
| `done` | 710/941/1295 | 任一 provider 返回 success 且 images>0 | ✅ |
| `failed` | 738/760/998/1301/1302 | 失败/异常/看门狗/等待区最终失败 | ✅ |
| `canceled` | 680/726/918/953/1250 | 用户取消/竞态兜底 | ✅ |
| `waiting` | 730/948/1285 | **超时(安全线)后保留待复核** | 保留(非终态) |

**内部流转态（适配器返回，未必落库）**：`submitted`(适配器内)、`success`(→done)、`error`(视频→failed/图片可能重试)、`timeout`(→waiting)、`canceled`、`throttled`(→DB 保持 running+入等待区)、`pending`(轮询中间)。`queued`/`processing` **不存在**——"排队"是进程内内存 Map，非 DB 枚举。

## 3. 提交与排队
- 提交即 `running`（无 pending/queued 中间态）。
- **waiting（等待区）= 进程内 `WAITING_AREA` Map（L1111）**，非 DB 状态枚举；DB 仍写 `running`。
- 触发：所有可用 provider 不可用 → `dispatchOne` 返 `throttled`(545,637) → `enqueueWaiting`(716,1143) + 持久化 `resume_meta->'waitingOpts'`(1159)。
- **持久化**：靠 `generation_tasks.resume_meta` JSONB；重启 `resumeWaitingArea`(825) 扫描 `resume_meta->'waitingOpts' IS NOT NULL OR error LIKE '%等待区%'`(832) 重建。
- **会员/VIP 优先级**：`PLAN_PRIORITY={free:0,pro:1,team:2}`(1107)；出队排序 `sort((a,b)=>(b.priority-a.priority)||(a.enqueueAt-b.enqueueAt))`(1277)；仅影响次序，不豁免计费/限额(1106)。

## 4. Provider 选择 / 失败切换 / 重试
- 选择：`pairs=(model×provider)` round-robin，`RR_POINTER` 全局指针(530-537)；`attemptOnAccount` 先查 isCold/bucket.tokens/conc(453-460)。
- 失败切换：`attemptOnAccount` 返 `null`→试下一 pair(536)；返 `timeout`/`failed`→**立即 return，不试下一账号**(540)。
- **最大重试次数 `MAX_RETRY=3`**(46)：整轮重试上限；退避 `sleep(200*(attempt+1))`(542)。等待区退避指数封顶 30s(1199)。
- **fallback 其他 provider**：✅ 有（跨 pairs round-robin）。但 generic 视频 `failed` 终态不会 fallback(540)；MiniMax/Volcano 因 T1 bug 反而会把"已明确失败"误当可重试去新建下一 provider 真实任务。

## 5. submit / poll / cancel
- **submit**：非 generic → `videoRouter.submit`→`ad.submit`；generic → `callEndpoint`(254)。成功即 `persistProviderTaskId`(779)。
- **poll**：`videoRouter.poll`→`ad.poll`→共享 `pollLoop`(shared.cjs:187)；generic 内联轮询(271-303)。
- **cancel 真正做了什么（cancelTask 1221）【源码已证实】**：
  1. 写内存信号 `cancelledTasks.add(taskId)`(1240) → 轮询下次检查即停(shared.cjs:193)
  2. `dequeueWaiting` 移出等待区(1242)
  3. `billing.releaseCredits` 释放 held 积分(1245)
  4. `updateTaskStatus('canceled')`(1250)
  5. `realtime.emitTaskUpdate` 推 SSE(1252)
  - **是否调用 provider 端取消 API：❌ 否**。全文无任何 provider 取消端点调用；仅停自身轮询。provider 端任务不予撤销（可能继续计费/占用 quota）。

## 6. 超时 vs 失败（资料库声称逐行核实 → 成立）【源码已证实】
- `timeout` 与 `failed` 是**不同状态**(490 vs 503)。
- **超时常量 90min**：generic 内联(268)、`pollLoop` 默认(shared.cjs:187)、等待区 `WAITING_MAX_WAIT_MS`(1114)。
- 超时后：仅 `updateTaskStatus('waiting')`，**无 releaseCredits**（728-731 / 946-949 / 1283-1287）→ 符合"超时返 waiting、绝不判失败、绝不退积分"。
- ⚠️ 副作用：`waiting` 任务积分**永久 held** 直至人工复核；看门狗 `scanStuckTasks` 只回收 `running`(>3h)，**明确不碰 waiting**(982,986-1001)。

## 7. 崩溃恢复【源码已证实】
- 启动调用点 `server.js:3615`(resumeRunningTasks) / `3619`(watchdog) / `3621`(resumeWaitingArea)。
- **在途视频恢复** `resumeRunningTasks`(798)：扫 `status='running' AND provider_task_id IS NOT NULL AND created_at>NOW()-6h`(805) → `resumeOneTask`(866) 重加载 provider/model → 据 `resume_meta.submittedAt` 续轮询(882-891) → `finalizeResumedTask`(912) 复用正常 commit/释放。
- **等待区恢复** `resumeWaitingArea`(825)：据 `resume_meta->'waitingOpts'` 重建并 `runWaitingPump`(852)。
- `provider_task_id`+`resume_meta` 为恢复唯一凭据。

## 8. 并发 / 限额【源码已证实】
- 全局并发 `GLOBAL_MAX=10`(29，可被 `settings.app.maxThreads` 覆盖 560)；`GLOBAL_ACTIVE` 计数(28)；满则 `sleep(120)`(534)。
- 单账号并发 `ACCOUNT_CONC_CAP=4`(45)；`concCap=min(modelConc??provider.max_concurrent||2, 4)`(459)。
- 令牌桶 `DEFAULT_BUCKET=20`/60s(41)；`DEFAULT_OP_COST={1k:1,2k:2,4k:20,video:20}`(42)；`capacity_model='unlimited'` 绕过(406)；`DEFAULT_COOLDOWN_MS=60000`(44)。
- **单用户限制：❌ 未在 dispatcher.cjs 内证实**（仅 `user_id` 用于归属/计费）。可能存在于 server.js 层，待核验。

## 9. 幂等 / 去重
- `idempotency_key`：`generation_tasks` 唯一索引 `ux_gt_idem`(server.js:271)；API 层同键 `failed`→释放旧 held 重生成、`running|done`→复用原 taskId 不重复 reserve(2411-2426)。
- `billing.cjs`/`accounting.cjs` 按 `idempotency_key` 去重。
- **`pending_ids`【源码已证实·仅存储回传，未用于回滚】**：仅 INSERT(661) + 前端读取回传(1032,1070,realtime:70)；全文无任何读取用于"取消时回滚已创建子任务/媒体"逻辑 → **推翻资料库"用于取消回滚"的声称**，它是前端占位 item id 列表，服务端取消不回滚媒体。

## 10. ★ T1 复核：MiniMax/Volcano 失败返回 `error` 而非 `failed`（真实 bug）【源码已证实】
| 适配器 | 生成端 failed 返回 | 证据 |
|---|---|---|
| agnes | `status:'failed'` | agnes.cjs:131 |
| minimax | `status:'error'` | minimax.cjs:85 |
| volcano | `status:'error'` | volcano.cjs:121 |
| generic(内联) | `status:'failed'` | dispatcher.cjs:291 |

- `attemptOnAccount`(450)：`res.status==='failed'`→立即终态不切账号(499)；其余非 success → `markReject+return null`(509)。
- MiniMax/Volcano 返 `'error'` → 命中 509 → **被当瞬时错误 markReject + 切下一账号新建真实 provider 任务**。
- 后果：provider 已明确失败却被当"临时不可用"→ 浪费 quota、不即时终态；若所有 provider 失败 → 多轮 null → `throttled` → 入 waiting(1285) → **积分永不释放、任务永不标 failed**（看门狗不碰 waiting）。
- 根因：`shared.cjs:218` `pollLoop` 把 `status==='error'` 也当终态返回，上游无法区分"provider 明确失败"与"网络/提交瞬态失败"。修复二选一：适配器在 provider 明确失败时返 `'failed'`（与 generic/agnes 对齐，改 minimax.cjs:85/volcano.cjs:121），或 dispatcher 对"已归一 canonical failed"做显式标记。
- **重构决策点**：建议修复（改适配器返 `failed`）并补 characterization 测试；若选择"精确复刻旧行为"须显式记为 INTENTIONAL_BREAKING_CHANGE。

## 11. 代码异味
- 巨型函数：`generateAsync`(648-775)、`attemptOnAccount`(450-526)、`runWaitingPump`(1262-1311)。
- catch 后继续：`attemptOnAccount` catch(520-525) 吞异常当资源不可用切账号；多处 `.catch(()=>{})` 静默。
- magic string/number：状态串散落硬编码无枚举；`90*60*1000`/`MAX_RETRY=3`/`ACCOUNT_CONC_CAP=4`/`GLOBAL_MAX=10`/`DEFAULT_BUCKET=20` 遍布。
- `fillTemplate` 非 string 一律 JSON.stringify(53) → 数字/布尔被包引号注入模板（隐式转换）。
