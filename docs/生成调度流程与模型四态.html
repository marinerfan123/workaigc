五、如何实时"展示"这些状态（已有后台接口）

  • GET /api/admin/routing/decide?model=&contentType=image —— 返回 chosen / ranking[] / rejected[]（每个被拒候选带 rejectedAt 卡在第几道门 + 人话原因）。这是"动态选了哪个模型"的现场回放。
  • GET /api/admin/.../account-states（server.js:2739，getAccountStates()）—— 每个 provider 账号的 tokens / conc / cooldownUntil / manualState / consecutiveRejects / cbState，可直接看谁在冷却、谁被熔断、谁被手动关。
  • GET /api/generate/queue-status —— 等待区积压与阈值（waitingAreaSize / WAITING_THRESHOLD / WAITING_MAX_RETRY），看哪些任务在被重试。

说明：以上为后台鉴权端点，需管理员 token。实时运行态（健康/熔断/并发/限流/冷却）存于 dispatcher 进程内 ACCT；PG 只存长期事实（enabled、manual_state、cooldown_ms）。单实例已够用；多实例（Server A/B/C）需按 MEMORY 第九节把该状态迁 Redis。

六、关键设计铁律（与你的架构原则一致）

  • 成败只听生成端：固定时间（90min 防僵尸安全线）只是保留待复核的安全线，绝不按时间判失败、绝不释放积分。这与超时铁律一致。
  • 重试不判失败：等待区重试达 WAITING_MAX_RETRY=10 仍无可用资源才关闭任务并释放积分（你 2026-08-13 推翻了"重试绝不判失败"的默认，加了全局上限）。
  • 熔断绝不发请求：OPEN 期间不扣令牌、不占并发、不记 attempt（cbAdmit 权威准入），根绝"一直打/一直失败/一直扣资源"。
  • 非阻断：路由层 / 熔断逻辑任何异常都退化为"原始顺序 + 放行"，绝不阻断生成主链路；ROUTING_V3_ENABLED=false 可秒级回退。
