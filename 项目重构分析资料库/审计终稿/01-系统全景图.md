## 3. 核心子系统职责与相互依赖

### 3.1 生成链路（dispatcher）
- **职责**：任务提交→模型×Provider 配对→令牌桶/并发门控→提交上游→自适应轮询→终态（`done/failed/canceled/waiting`）→崩溃 resume。
- **依赖**：`billing`（reserve/commit/release）、`accounting`（recordConsumption）、`realtime`（SSE 推送）、`modelhub resolver`（模型身份解析）、PG `generation_tasks`、上游 Provider。
- **关键事实**：提交即 `running`（无 pending/queued）；等待区为进程内 `WAITING_AREA` Map，DB 仍记 `running`；超时（90min）入 `waiting` **绝不判失败、绝不退积分**；看门狗只回收 `running>3h`，**不碰 waiting**（【源码已证实】HIGH，见 06）。

### 3.2 计费链路（billing + accounting）
- **职责**：双余额（reward 优先→recharge 回退→不足 402）三段式 `reserve→commit/release`；双边记账（`consumption_ledger`：客户收费 vs 平台成本→margin）。
- **依赖**：PG `users.credits`/`credit_transactions`/`consumption_ledger`、`settings.app`（成本兜底/分成率）。
- **关键事实**：`users.credits` 是 `GENERATED ALWAYS AS (reward_credits+recharge_credits) STORED` 派生列，**不可写/不可扣**，真实池仅 2 个（【数据库已证实】HIGH）；commit/release 为 SELECT→INSERT 非原子、无事务、无唯一约束（【源码已证实】HIGH，见 07）。

### 3.3 支付链路（payments + webhook）
- **职责**：创建订单（后端金额权威取 `topup_packages`）→ 等待支付 → 异步 webhook 验签入账（本金+bonus 入 recharge 池）。
- **依赖**：PG `recharge_orders`/`payment_providers`/`payment_settings`/`webhook_events`/`payment_audit`、`crypto.cjs`（AES-256-GCM）、easypay 网关。
- **关键事实**：webhook 四关 fails-closed + 幂等去重（webhook_events 唯一索引）；但**绕过 billing 直接裸 SQL 入账**（【源码已证实】HIGH，见 08 §7）；`expired` 订单仍可被迟到真实支付入账（缺口 A）。

### 3.4 实时链路（realtime）
- **职责**：生成任务终态经 SSE 推送给对应用户（按 `u:${userId}` 隔离）。
- **依赖**：进程内 `EventEmitter`（无 Redis pub/sub）；dispatcher 在终态调用 `emitTaskUpdate`。
- **关键事实**：纯内存单进程，**不跨实例**；前端以 `EventSource` + 每 3s 轮询兜底双保险（对 SSE 零信任）；连接即回灌在途快照（【源码已证实】HIGH，见 11）。

### 3.5 权限链路（auth + appGateway + admin）
- **职责**：登录签发 HS256 JWT（sid cookie）；`appGateway` 全局门；`requireAdmin` 放行 `admin|system`。
- **关键事实**：`/api/token` 公开返回全局 API_TOKEN；dev 模式下 Bearer 优先于 cookie → 前端全流量以 `__system__` 身份运行，**整层 RBAC 失效**（【源码已证实】HIGH，见 03 §1、10 P0-A/P0-B）；JWT 密钥缺失回退 `'dev-only-change-me'` 可伪造任意身份（10 P0-B）。

## 4. 三条端到端数据流

### 4.1 一次文生图任务的完整生命周期
```
[前端] GenerationBar → POST /api/generate {model, prompt, idempotencyKey}
   │
   ▼ server.js handleAPI (L2424)
[网关] appGateway → realUser 校验(2405) → 限流(2396)
   │
   ▼ 幂等键处理：同键 failed→释放旧 held 重生成；running|done→复用(2411-2426)
[模型] modelHubResolver.resolveModelIdentity (2430) → 查 models 计费维度(2437)
   │
   ▼ [计费] billing.resolvePayment (2446)  → 不足返 402 {code:NEED_RECHARGE}
[计费] billing.reserveCredits (2459) 预扣 held（reward 优先→recharge 回退）
   │
   ▼ [调度] dispatcher.generateAsync (2522, fire-and-forget)
        ├─ INSERT generation_tasks status='running' + cost/cost_pool/idempotency_key (661)
        ├─ generate(549): 组装 (model×provider) pairs, round-robin RR_POINTER
        ├─ dispatchOne(529): 令牌桶/并发门控
        ├─ attemptOnAccount(450): 查 isCold/bucket.tokens/conc → provider.submit
        ├─ 视频/图片适配器 → 上游 Provider 返 provider_task_id (persist 779)
        ├─ pollLoop(shared.cjs:187): 自适应轮询(前1min基线→>15min 60s封顶)
        │
        ├─ 成功 → finalizeTask:
        │      commitCredits(691) + accounting.recordConsumption(699)
        │      + 落 media/result + 标 done(710)
        │      → realtime.emitTaskUpdate(userId,{status:'done',result}) (SSE)
        │
        ├─ 失败 → releaseCredits(734) + 标 failed(738)
        ├─ 超时(90min) → 标 waiting(728)【不退积分】
        └─ 取消 → releaseCredits(1245) + 标 canceled + SSE
   │
   ▼ [前端三态]
   ├─ SSE 推送 (GET /api/generate/stream, text/event-stream)
   ├─ 3s 轮询兜底 GET /api/generate/status/:id
   └─ 超时(视频95min/图片3.5min)仍非终态 → 保留 pending「生成中」
```

证据：【源码已证实】HIGH（见 02 F-001、06 报告 §1）。

### 4.2 一次计费扣费链路（双余额三段式）
```
reserve（handler 同步）                commit（成功回调）          release（失败/取消/看门狗）
─────────────────────                ───────────────────         ──────────────────────
billing.reserveCredits:               billing.commitCredits:      billing.releaseCredits:
 UPDATE users SET                       INSERT credit_transactions  SELECT→INSERT(非原子)
  pool = pool - $cost                  (kind='spend', balance_after)
  WHERE id=$2 AND pool>=$cost          UPDATE users SET pool+=$cost
（行级原子防负）                       （reward 或 recharge 池）
                                        accounting.recordConsumption
                                         (双边记账, 同键 SELECT→INSERT)
扣费顺序 resolvePayment:
 1) supportsReward 且 reward>=required → reward 池
 2) 否则 recharge>=cost → recharge 池
 3) 都不够 → 抛 INSUFFICIENT / NEED_RECHARGE → 402
```
**⚠ 资金风险**：commit/release 为 SELECT→INSERT 两步、无 DB 事务、无 (ref,kind)/(idempotency_key) 唯一约束 → TOCTOU 双退/双记账；失败键复用不清理流水 → 永久损失积分（【源码已证实】HIGH P0，见 07 §6、15 P0-1/P0-2）。
证据：【源码已证实】HIGH（07 报告 §2–§4）。

### 4.3 一次充值支付链路
```
[前端] RechargePage → POST /api/credits/orders {method, amount}
   │   server.js → payments.cjs createOrder (59)
   │   - 金额/bonus 后端权威取 topup_packages (73-83)，杜绝前端篡改赠送
   │   - sign = hmac(sha256, SIGN_SECRET, `${payOrderNo}:${amount}:${channel}`) (138)
   │   - INSERT recharge_orders(pay_order_no, sign, expired_at, bonus) status='pending'
   │   - 无 provider → 503 (无 DEV/模拟回退)
   ▼ 用户跳转支付
[支付网关] easypay 收款 → 异步回调
   ▼ POST /api/credits/webhook/:type  (网关前公开放行)
[webhook 四关 fails-closed]
   第0关 通道存在            → 否 400
   第1关 verifyWebhook 验签  → 失败 400 + payment_audit(verify_fail)
   第2关 金额+状态守卫       → 不一致 ROLLBACK+audit+400；已 paid→alreadyPaid
   第3关 幂等去重            → webhook_events UNIQUE 冲突 → alreadyPaid
   ▼ 单事务入账 (128-168)：
   1) 订单置 paid
   2) 裸 SQL: UPDATE users SET recharge_credits+=本金 RETURNING credits
   3) INSERT credit_transactions(kind='grant', pool='recharge', ref=o.id)
   4) bonus>0 → 再 UPDATE recharge_credits+=bonus + 第二条 grant 流水
   5) payment_audit('paid') + COMMIT
   ▼ [前端] 轮询 GET /api/credits/orders/:payOrderNo → status='paid' 切成功态
```
**⚠ 缺口**：webhook 绕过 billing 直接裸 SQL（两套记账语义漂移）；`expired` 订单不硬拒、迟到真实支付仍入账（非双付，但语义待产品确认）（【源码已证实】HIGH，见 08 §6/§7）。
证据：【源码已证实】HIGH（08 报告 §3–§8）。

## 8. 审计发现摘要（系统整体健康度的最关键结论）

1. **【P0·认证全面失效】`/api/token` 公开返回全局 system 令牌 + JWT 密钥回退 `'dev-only-change-me'`**
   当前 `.env` 无 `NODE_ENV`/`JWT_SECRET` → dev 模式下前端每个请求以 `__system__` 身份运行，`requireAdmin` 对**任意访客可达**；且可离线伪造任意 `role:'admin'` 会话。整层 RBAC 形同虚设，属远程未授权管理员接管。【源码已证实】HIGH（见 03 §1/§3.1、10 P0-A/P0-B）。**重构优先级最高**。

2. **【P0·资金安全】计费/记账无 DB 事务、无唯一约束，存在 TOCTOU 双退/双记账与漏退款**
   `credit_transactions(ref,kind)` 与 `consumption_ledger(idempotency_key)` 仅非唯一索引；commit/release、recordConsumption 均为 SELECT→INSERT 非原子；失败键复用不清理流水致永久损失积分。`users.credits` 为 STORED 派生列（已排除第三余额双花，但双池仍脆弱）。【源码已证实】HIGH（见 07 §6、15 P0-1/P0-2）。

3. **【P0·生成链路缺陷】T1 bug：MiniMax/Volcano 失败返回 `error` 被当瞬时错误 failover**
   上游已明确失败却被反复切换账号新建真实任务，全失败时入 `waiting` → 积分**永不释放、任务永不标 failed**（看门狗不碰 waiting）。同时前端 `cancelled`(双 l) 与后端 `canceled`(单 l) 拼写不一致，致跨标签取消失效、卡片卡「生成中」。【源码已证实】HIGH（见 06 §10、09 §5、11 §3.1、12 C6）。

4. **【中·可扩展性与 DR】核心状态全进程内 + 数据库单点**
   SSE/令牌桶/等待区为单实例内存态（多实例实时性退化为轮询级、易 429 风暴）；PG 单容器单卷、无 WAL 归档/副本/故障转移；仅有手工备份无自动调度；部署无回滚机制。【源码已证实】HIGH（见 05 §6、11 §4、14 报告）。

5. **【中·测试与契约脆弱】零有效测试 + 隐式文本契约绑定前后端**
   8 个测试因框架不匹配实际 0 可执行，资金/调度/支付/鉴权核心无安全网；前后端强耦合于错误串 `API <status>:`、`code` 字面量、`SNAKE_MAP` 字段映射、`canceled/cancelled` 等隐式契约，改动任一即静默失效。【源码已证实】HIGH（见 15 报告、12 §2 C1–C6）。

> 总基调：系统**功能厚度足够、单体架构可读**，但**资金与认证两条生命线存在 P0 级缺陷**，且**无任何有效测试网**兜底；重构应以「先补认证铁壁 + 资金事务/唯一约束 + 字符化测试」为前置条件，再处理生成状态机 bug 与水平扩展硬限制。其余详见 02–15 各专项底稿。
