# 07 · 计费资金状态机（墨灵AI 重构前体检）

> 证据等级：【源码已证实】（billing.cjs / accounting.cjs / dispatcher.cjs / server.js）+【数据库已证实】（users 生成列、约束实测）。
> 本文件为只读取证。资金为最高风险域，结论均已交叉核验。

## 1. 用户余额种类（已澄清"三余额"本质）
- **`users.credits` = `GENERATED ALWAYS AS (reward_credits + recharge_credits) STORED`**【数据库已证实：`is_generated=ALWAYS`】→ **派生总计列，不可写、不可扣**。
- **`reward_credits`（奖励池）**：注册赠送/平台发放（billing.cjs:4-5）。
- **`recharge_credits`（充值池）**：真钱充值/后台调额。
- **真实可扣池 = 2 个**（reward + recharge）；`credits` 仅展示用。
- 结论：系统无"独立第三余额池"，不存在经 `credits` 的双花路径。

## 2. 双余额扣费顺序【源码已证实】`billing.cjs:11-29` `resolvePayment`
1. 若 `supportsReward` 且 `reward >= rewardRequired` → 走 **reward 池**(17)
2. 否则若 `recharge >= creditCost` → 回退 **recharge 池**(18)
3. 都不够 → 抛 `INSUFFICIENT`(20-22)；不支持奖励则只能 recharge，不够抛 `NEED_RECHARGE`(25-28)
- 顺序：**奖励池优先 → 充值池回退 → 不足报错**。完整回退（非部分混扣）。

## 3. 三段式流程（reserve / commit / release）
| 阶段 | 函数 | 位置 | 触发 |
|---|---|---|---|
| reserve 预扣 | `reserveCredits` | billing.cjs:32 | `/api/generate`(server.js:2459)；shop(shop.cjs:56) |
| commit 结算 | `commitCredits` | billing.cjs:58 | 异步成功(dispatcher.cjs:691)、resume(finalizeResumedTask:926)、等待区(1294)、sync(server.js:2496)、shop(174/246) |
| release 退还 | `releaseCredits` | billing.cjs:70 | 异步失败(734)、异常(758)、resume失败(957)、看门狗(996)、取消(1245)、server 各失败回滚(2512/2516/2524/2529)、shop(158/163/171/188) |

- `generation_tasks.cost` / `cost_pool`：INSERT 时写(dispatcher.cjs:661-663)，值来自 `genOpts.cost`(=pay.amount,server.js:2480) 与 `cost_pool`(=pay.pool,server.js:2481)；commit/release 传 `cost`+`cost_pool`。
- **reserve 在 handler 同步发生；commit/release 在后台回调/看门狗/取消/shop 发生**（资料库称"reserve 只在 generate"不完整——shop/sync 也三段式）。

## 4. 幂等机制【源码已证实】
- 任务级：`generation_tasks.idempotency_key` 唯一索引 `ux_gt_idem`（server.js:271，WHERE NOT NULL）。
- 流水级：`billing.cjs` `_hasPosted(ref,kind)` = `SELECT 1 FROM credit_transactions WHERE ref=$1 AND kind=$2 LIMIT 1`(48-55)；commit/release 先查再插，存在跳过(60,72)。
- **⚠️ 无 DB 事务、无 `FOR UPDATE`**：全仓 grep billing/accounting 零命中 BEGIN/COMMIT/FOR UPDATE（仅 db.cjs:184、payments/webhook.cjs、server.js 注册登录有事务）。
- reserve 防负：靠 `UPDATE ... SET col=col-$1 WHERE id=$2 AND col>=$1` 条件更新(billing.cjs:35-38)（PG 行级原子）。
- commit/release 是 **SELECT→INSERT 两步、非原子**。
- `credit_transactions` **无 (ref,kind) 唯一约束**（仅非唯一索引 ix_ct_ref，server.js:248）。

## 5. 退款路径（失败/取消/异常/超时/provider失败/崩溃）
- **失败退款**：dispatcher.cjs:734（异步失败）、957（resume失败）、1300（等待区失败）→ releaseCredits。
- **取消退款**：cancelTask(1245) → releaseCredits；`amount<=0` 直接 return true(billing.cjs:71)。
- **异常退款**：`.catch`(758)、server.js:2516/2524/2529。
- **超时处理【核实成立】**：timeout→标 `waiting`，**绝不判失败、绝不释放积分**(728-731/946-949/1284-1287)；看门狗只回收 running(>3h)，不碰 waiting。
- **provider 失败**：走 failed 分支 release(733-734)。
- **服务崩溃恢复**：视频 provider_task_id 已落库 → 启动 resumeRunningTasks 续轮询，终态同正常；图片/孤儿看门狗 scanStuckTasks 扫 running>3h 强制 failed+release(983-1001)。

## 6. ★ 资金风险点（P0，逐条带证据）
1. **【漏退款】失败键复用**：server.js:2415-2418 重试 `failed` 任务只 `releaseCredits`+删 `generation_tasks` 行，**不清理 `credit_transactions`**。第二次若再失败，`releaseCredits` 的 `_hasPosted`(billing.cjs:72) 命中第一次残留 release 行 → 返回 true → **跳过释放，用户永久损失 `cost` 积分**。
2. **【重复退款 TOCTOU】**：releaseCredits SELECT→INSERT 非原子、无 (ref,kind) 唯一约束(server.js:248) → 并发两次 release 可双过 `_hasPosted` → 余额双加。
3. **【双记账】**：consumption_ledger.idempotency_key 仅非唯一索引 ix_cl_idem(server.js:656)；recordConsumption SELECT→INSERT 无事务(accounting.cjs:62-68) → 并发同键可双插，margin 虚高。
4. **【死代码/阈值冲突】** `findDanglingReserves`(billing.cjs:84) 定义(running>30min 释放 held)但**全仓零调用**；若启用将违反"超时不退积分"(90min 安全线)；且与看门狗 3h 阈值形成 30/90/180min 三套阈值。
5. **【并发 reserve 双扣窗口】**：server.js:2411 SELECT 与 dispatcher.cjs:663 INSERT 非锁定，两并发同键可都过查重都 reserve，靠 ux_gt_idem 唯一索引在 INSERT 拦第二笔并触发 release 回退(server.js:2523) → 净零但产生多余流水行；边缘：若第二笔在 reserve 后、insert 失败前崩溃，留一笔未关联任务的 held。
6. **【账/余额分离】** recordConsumption 不碰用户余额(accounting.cjs:98-108)，billing 不写 ledger；两边仅靠 idempotencyKey 命名约定对齐(dispatcher.cjs:702) → 任一侧 bug 不被另一侧发现。
7. **【balance_after 取总计列】** commitCredits 的 balance_after 取 `users.credits`(STORED 总计, billing.cjs:63) 非按池 → 支付侧同类瑕疵（入账流水 balance_after 取 credits 列而非 recharge_credits 列）。
8. **【price 分摊舍入】** `alloc=round(cost*units/totalUnits)` 按组分摊(dispatcher.cjs:697) → 多组求和可能 ≠ cost，仅账务层偏差，不影响余额。

## 7. accounting.recordConsumption 解剖【源码已证实】
- 参数(accounting.cjs:55-58)。**scope**：`'user'|'system'`；`system` 含义＝"客户收费传 0 如实显示为平台成本"(48,53)。
- **★ 推翻资料库 A11**：实测 `recordConsumption` 全部调用方均传 `scope:'user'`（dispatcher.cjs:699,932 / shop.cjs:179 / server.js:2733(optimize-prompt),2878(translate-prompt) / reference-style-audit.cjs:191），**`scope='system'` 在仓库内无任何调用方触发**。资料库称"系统调用 scope='system'"不成立——系统成本以 `customerChargeCredits:0` 实现，非 scope。
- 双边记账：后台量 `backend_cost_cents`（优先 model_cost_rates 精确率，否则 settings.app.defaultBackendCost 兜底，71-90）；客户量 `customer_charge_credits`→`customer_charge_cents=credits*creditToCents`(94-95)；`margin_cents=客户-后台`(96)。
- 字段一一对应 consumption_ledger(98-108)；幂等键同键已存在则 `{skipped:true}`(63-68)；try/catch 容错不阻断主链。

## 8. 与资料库交叉核验
- **一致**：A2 STORED 生成列(server.js:233)、A3 超时不退积分(dispatcher:729/946-949/1284-1287)、A7 取消释放+终态(dispatcher:1232-1250)、B 双余额 SNAKE_MAP(server.js:816)。
- **冲突/补充**：A1 "reserve 只在 generate" 不完整（漏 shop/sync）；A11 "scope='system'" 不成立（实测全 user）；`findDanglingReserves` 死代码（资料库标"对账兜底"但实际 0 调用）。

## 9. 重构建议（资金域，P0）
- 为 `credit_transactions(ref,kind)` 与 `consumption_ledger(idempotency_key)` 加 **DB 唯一约束**（`INSERT ... ON CONFLICT DO NOTHING`）。
- 把 `resolvePayment/reserve/commit/release` 包进真实 `BEGIN/COMMIT`（至少 commit/release 与 ledger 写同事务）。
- 失败键复用时**清理旧 credit_transactions 行**或改用 ON CONFLICT。
- balance_after 明确按池记录，避免取总计列混淆。
- 删除或正确接入 `findDanglingReserves`，统一超时阈值语义。
