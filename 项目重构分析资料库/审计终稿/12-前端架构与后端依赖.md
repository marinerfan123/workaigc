## 1. 前端整体架构

### 1.1 路由结构

- 入口：`src/index.tsx` 用 `createRoot` 渲染 `<StrictMode><BrowserRouter><App/></BrowserRouter></StrictMode>`；启动时立即 `initAuth()` 恢复会话（不阻塞渲染）；并显式 `window.history.scrollRestoration='manual'` + `ScrollToTopOnRoute` 路由级回顶（【源码已证实】HIGH）。
- 路由表集中在 `src/app.tsx`（`<Routes>`），采用**多层嵌套布局壳 + 守卫**模式：
  - 独立页（不走壳）：`/`、`/login`、`/register`、`/setup`、`/recharge`。`/` 套 `FirstRunGate`——首访若 `getSetupStatus().initialized===false` 自动跳 `/setup`。
  - 前台工作台壳 `<Layout>`：`/workspace`、`/library/:category?`、`/characters`、`/model-hub`(RequireAdmin)、`/model-console`、`/edit/:id`、`/account`、`/user/:id`(公开)，以及 Help/Docs/Changelog/Tutorials/About/Guide/Privacy(公开) 与 Feedback/Report(RequireAuth)。
  - 管理后台壳 `/admin` `<AdminLayout>`（RequireAuth + 角色细判）：`agents/users/samples/reference-styles/models/transactions/skills/ecommerce/monitor/finance/payment-settings/logs/errors/monitoring/settings/storage/ledger/recommend/studio` 等大量子路由。
  - 独立监控弹窗 `/monitoring/:tab`（RequireAdmin）。
  - 创作工作室壳 `/studio` `<StudioLayout>`：`index`、`/:projectId`。
  - 电商壳 `/shop` `<ShopLayout>`：`product/:id`、`cart`、`checkout`、`orders`、`seller`（下单相关 RequireAuth）。
  - 兜底 `*` → `NotFoundPage`。
- 守卫组件：`RequireAuth`（会话缺失跳 `/login`）、`RequireAdmin`（`model-hub` 用，其余后台交给 `AdminLayout` 渲染无权限提示页，避免 F5 被直接踢回主页）。【源码已证实】HIGH。

### 1.2 状态管理方案

- **不使用 zustand / redux / recoil / jotai 等第三方状态库**（全仓检索无相关 import，【源码已证实】HIGH）。
- 认证态：自研**模块级 external store**（`src/services/authStore.ts`），用 React 19 的 `useSyncExternalStore(subscribeAuth, getAuthState, getAuthState)` 暴露 `useAuth()`；模块内 `state` 单例 + `listeners` 发布订阅，`login/register/logout/refreshUser/initAuth` 改 state 后 `emit()`。这是全站唯一的"全局可订阅"状态（【源码已证实】HIGH）。
- 其它状态：绝大多数为**组件本地 `useState`/`useEffect`**；UI 基础组件（shadcn 系）用 **React Context**（`chart.tsx`/`carousel.tsx`/`form.tsx`/`sidebar.tsx`/`toggle-group.tsx`/`input-otp.tsx`），仅限组件内部作用域（【源码已证实】HIGH）。
- 结论：状态管理是"轻量自研 external store（仅认证）+ React Context（UI 组件）+ 大量本地 state"的三层混合，**没有集中式 store 层**。重构若引入 zustand/redux，需重新评估哪些本地 state 应上提到全局（如生成任务列表、OSS 配置、购物车），但当前并非阻塞项。

### 1.3 API 客户端统一入口

- **唯一入口是 `src/services/api.ts`**（约 1329 行）。约定：
  - 模块级 `API_BASE`/`API_TOKEN`，由 `ensureApi()` 自动发现后端：取 `window.location` 同域 → `GET /api/token`（带 `credentials:'include'`）拿 token；发现失败则降级到"内置默认数据（不持久化）"（【源码已证实】HIGH）。
  - 底层 `apiFetch<T>`：`fetch(\`${API_BASE}${path}\`, {credentials:'include', headers})`；**非 2xx 一律 `throw new Error(\`API ${res.status}: ${text.slice(0,200)}\`)``**（api.ts:29-33）——这是全站错误字符串契约的总源头。
  - 几乎所有业务函数都是 `try { return await apiFetch(...) } catch { return <降级空值> }` 形态：失败时返回 `[] / {} / null / {ok:false}`，**静默兜底**是普遍约定（api.ts 全文，【源码已证实】HIGH）。
- 另有 `src/services/genericClient.ts`：直接**前端↔服务商**的 OpenAI 兼容/自定义端点调用（图片/视频/文本生成、模型列表、JSONPath 字段抽取），用于"本站后端代理之外的直接打通"场景（如 OSS 配置向导、技能试跑）。它**不**走 `/api` 代理，直接持 `apiKey` 请求 `provider.baseUrl`，是另一条独立通道（【源码已证实】HIGH）。
- `src/app.tsx` 末尾从 `@/pages/Admin/UsersPage` 再导出 `apiAddToCart/apiGetCart/...` 等——即**购物车/订单类 API 定义在页面文件里，再被 api.ts 统一再导出**，以维持"`@/services/api` 为唯一入口"。这是"API 入口物理分散、逻辑集中"的隐患（见 §4）。

## 2. 前端对后端的隐藏依赖 / 耦合点（核心章节）

> 编号 C1–C9，每条标注【证据等级】+ 置信度，并给出前端/后端双向证据位置。

### C1 · 错误文本格式契约：`API <status>: <text>`（字符串解析）
- **契约**：`apiFetch` 在非 2xx 时抛出 **`API ${res.status}: ${text}`**（api.ts:29-33，【源码已证实】HIGH）。多处前端**按此字符串反解**业务信息：
  - `apiGenerate`（api.ts:466）用正则 `/^API \d+:\s*(\{[\s\S]*\})\s*$/` 从错误消息里抠出 JSON body 的 `code` 字段。
  - `apiCancelGeneration`（api.ts:501-509）用 `msg.indexOf('{')` 再 `JSON.parse` 抠出 `{error, code}`。
- **风险**：这是"用异常消息文本当协议"的硬耦合。若后端改错误文案格式、或在 `API 4xx:` 前后加字符（如换行/前缀），`apiGenerate` 的 `code` 抽取与 `apiCancelGeneration` 的 `error/code` 抽取会**静默失败**（catch 兜底返回 undefined，前端误判为通用错误）。重构若统一错误体（如改为结构化 Exception），必须同步改这两处字符串解析，否则"余额不足/取消失败"等业务分支全失效。
- 证据等级：【源码已证实】；置信度：**HIGH**。

### C2 · 业务错误码契约（code 字段语义）
- **契约**：后端在 402/409 等非 2xx 的 JSON body 中返回 `code` 字符串，前端按字面量分支：
  - `NEED_RECHARGE`（不支持赠送且充值不足）、`INSUFFICIENT`（支持赠送但双池皆不足）：`api.ts:463-467`（抽取）、`GenerationBar.tsx:181/188/1029/1127/1131/1193/1198`、`reason` 字面量贯穿 `GenerationBar` 状态机。
  - `NO_REASONING_MODEL`：`GenerationBar.tsx:1339/1378`。
  - `already_initialized`：`SetupWizardPage.tsx:85`（`e.code === 'already_initialized'`，后端 fails-closed 防重复初始化）。
- **风险**：这些 `code` 是前后端**隐式约定**，无类型/枚举收敛（后端是运行期字符串，前端是字面量散落）。重命名任一 code（如 `INSUFFICIENT`→`BALANCE_INSUFFICIENT`）会让对应弹窗/拦截逻辑失效且无编译报错。
- 证据等级：【源码已证实】；置信度：**HIGH**。

### C3 · HTTP 状态码契约（按 status code 分支）
- **契约**：前端按具体状态码处理：
  - `AuthModal.tsx:49`：`msg.includes('409')` → toast "该邮箱已注册"（**用错误文本是否含子串 '409' 判断**，极脆弱）。
  - `GenerationBar` 多处：`/402|积分不足/.test(err)`（api.ts:463、GenerationBar:1127/1193）——同时依赖"402 状态"与中文字样"积分不足"。
  - 后端固定返回 402（余额不足）、409（重复/冲突）、401（未登录）、503（支付通道/DB 不可用）等，前端据此分支。
- **风险**：`AuthModal` 的 `includes('409')` 是典型"文本嗅探"反模式——只要后端消息里出现数字 409（哪怕在别的语境）就会误判；若后端把冲突码改成 400+错误体，注册冲突提示直接消失。`/402|积分不足/` 对"积分不足"中文文案改动同样敏感。
- 证据等级：【源码已证实】；置信度：**HIGH**。

### C4 · SNAKE_MAP 后端蛇形→驼峰映射缺口（字段 undefined 假死）
- **契约**：后端**显式**维护一张 `SNAKE_MAP`（`server/server.js:830-845`），把 PG 蛇形列名映射成驼峰 JSON 键：
  `full_url→fullUrl, oss_url→ossUrl, oss_object_key→ossObjectKey, oss_uploaded→ossUploaded, avatar_url→avatar, reference_images→referenceImages, base_model→baseModel, is_favorite→isFavorite, is_deleted→isDeleted, created_at→createdAt, error_message→errorMessage, failed_at→failedAt, file_size→fileSize, character_id→characterId, is_default→isDefault, default_key→defaultKey, tags→tags, owner_id→ownerId, current_stage→currentStage, cover_url→coverUrl, ...`（另有 providers/oss 大量映射）。
- **前端依赖**：`data/media.ts` 的 `IMediaItem` 与全站消费代码**全部按驼峰**访问（`m.thumbnail/m.fullUrl/m.ossUrl/m.status/m.errorMessage/m.failedAt`、`c.referenceImages/c.baseModel/c.avatar` 等）。前端**没有任何 snake→camel 转换层**，完全信任后端已映射。
- **风险（即任务所说的"缺口导致字段 undefined 假死"）**：
  - 该映射表是**前后端之间的隐性字段契约**。后端一旦新增 DB 列但**漏加进 SNAKE_MAP**，前端对应驼峰字段即 `undefined` → 渲染 `.map` 崩溃或"假死/空白/无限 loading"。
  - 前端已有两处**防御性 normalize** 暴露了此风险曾真实发生：`normalizeCharacters`（api.ts:280-297，强制 `referenceImages` 为数组防 `.map` 崩）、`IMediaItem.status` 默认 `'success'`、图片用 `Image` 组件兜底空 src。
  - 重构若做"前后端共用类型"（如把 `IMediaItem` 提升为 `@shared` 的契约类型），必须让 `SNAKE_MAP` 与前端类型**单一真相来源**对齐，否则新增字段会再次踩 undefined。
- 证据等级：【源码已证实】（前后端双向取证）；置信度：**HIGH**。

### C5 · SSE 实时通道约定（事件名 + payload 字段）
- **契约**：
  - 端点 `GET /api/generate/stream`（server.js:2592），按 `userId` 订阅；连接即回灌在途快照（解决刷新/连接前漏事件）。
  - 推送格式（`server/realtime.cjs:38`）：**默认（无名）SSE 事件**，`res.write(\`data: ${JSON.stringify(payload)}\n\n\`)`——即 `event:` 缺省（前端用 `es.onmessage` 而非 `es.addEventListener('xxx')`）。
  - payload 形状 = `TaskUpdate`（frontend `useGenerationStream.ts:9-22`）：`{taskId, status, result?, error?, pendingIds?, model?, prompt?, count?, contentType?, clientMeta?, createdAt?, completedAt?}`，其中 `result` 含 `images/source/usedProviders/videoUrl`。
  - 后端 `dispatcher.cjs` 实际 `emitTaskUpdate` 字段：`{taskId, status, error}` / `{taskId, status:'done', result}` / `{taskId, status:'waiting'}` / `{taskId, status:'running', error}`（dispatcher.cjs:674/704/713/720/733/757 等）。
- **风险**：
  - 若后端改为**命名事件**（`event: task-update`）或改变 `data:` 包裹结构，前端 `es.onmessage = JSON.parse(ev.data)` 会整段失效（且 useGenerationStream 对非法帧是 `catch{}` 静默忽略 → 完成通知丢失，仅剩 3s 轮询兜底仍可用，但实时性退化）。
  - `useGenerationStream` 的**容错设计本身已是重要耦合说明**：它**同时**监听 SSE + 每 3s `apiGetGenerationStatus` 轮询兜底（useGenerationStream.ts:88-98），任一命中终态即 resolve——这是"对 SSE 零信任"的工程取舍。重构时切勿移除轮询兜底，否则 SSE 一抖就丢完成通知（【源码已证实】HIGH）。
  - 同上，终态判定依赖 `status` 取值集合（`done/failed/cancelled/not_found`），与 C6 直接耦合。
- 证据等级：【源码已证实】（前后端双向）；置信度：**HIGH**。

### C6 · `canceled` / `cancelled` 拼写不一致（与 11 号文档联动）⚠️ 最高危
- **现象（双向取证）**：
  - **后端**统一使用**单 l `canceled`**：
    - `server/dispatcher.cjs:674` `updateTaskStatus(pgPool, taskId, 'canceled', ...)` + `realtime.emitTaskUpdate(user_id, {taskId, status: 'canceled', ...})`
    - `dispatcher.cjs:720`、`dispatcher.cjs:921` 同样 `status: 'canceled'`（写入 DB + 推 SSE）。
    - `server.js:2565` 注释："标记 canceled + 推送 SSE canceled"。
    - 即 DB 落库值、SSE payload、状态接口返回值**全是 `canceled`（单 l）**。
  - **前端**统一使用**双 l `cancelled`**：
    - `src/hooks/useGenerationStream.ts:11` `TaskUpdate.status` 联合类型含 `'cancelled'`；
    - `useGenerationStream.ts:84/92` 终态判定 `u.status === 'cancelled'`、`st.status === 'cancelled'`；
    - `src/components/GenerationBar.tsx:570` `if (final.status === 'cancelled')`；
    - `src/data/media.ts:20` `IMediaItem.status` 含 `'cancelled'`。
    - （注：`src/services/genericClient.ts:263/293` 的 `'canceled'` 是比对**上游服务商**返回状态，与本站后端无关，属正确用法。）
- **后果（严重）**：用户取消生成任务后——
  - SSE 推送 `status:'canceled'` → 前端 `u.status === 'cancelled'` **永不匹配** → SSE 路径不结算；
  - 轮询兜底 `apiGetGenerationStatus` 返回 DB 值 `'canceled'` → `st.status === 'cancelled'` **同样不匹配** → 轮询路径也不结算；
  - 任务只能等 `waitForTask` 的 **95 分钟超时**（useGenerationStream.ts:61）才 `settle(last)`（last 仍为 running）→ **取消的卡片在 95 分钟内一直显示为"生成中/pending"，不移除、不释放视觉状态**。等价于"取消功能在 UI 层基本失效"。
  - 这很可能是线上"取消后卡片卡住/积分疑似未释放"类问题的根因之一；与 11 号文档（取消/拼写契约）联动，建议作为**重构 P0 修复项**。
- 修复方向（仅建议，不改码）：前后端统一为同一拼写（推荐后端改为 `cancelled` 双 l 以匹配前端既有类型，或反之），并把 `status` 取值收敛为 `@shared` 共享枚举。
- 证据等级：【源码已证实】（前后端双向精确取证）；置信度：**HIGH**。

### C7 · `<img>` 必须走 `ui/image.tsx` 的 onError 兜底约定（裸 img 绕过）
- **契约**：`components/ui/image.tsx` 是图片渲染唯一兜底组件，内置两条关键防线（image.tsx:137-151）：
  1. `src` 为空/非字符串 → **直接 `return null`**，禁止渲染 `<img src="">`（否则浏览器把空 src 当作"加载当前页"，整页被覆盖、React 子树卸载，WorkspacePage/MediaCard 图片瞬间消失——即注释所述 #576）。
  2. `onError` → `setErrored(true)` 后 `return null`，不渲染破图图标，占位交给调用方（红卡/spinner）。
  - `src` 变化时 `useEffect` 重置 `errored`，避免"换有效 URL 仍卡空白"的残留态（image.tsx:125-127）。
- **风险**：多处**裸 `<img>` 绕过了该约定**，其中 `SamplesPage.tsx:181` 直接用 `s.thumbnail` 渲染 `<img src={s.thumbnail}>`——一旦 `thumbnail` 为空，即触发 image.tsx 专门消灭的 #576 整页重载 bug；`UserPage.tsx:124`、`MonitoringPage.tsx:348`、`ModelConsole.tsx:582`、`CheckoutPage.tsx:85`、`SellerPage.tsx:85`、`CartPage.tsx:74`、`SamplesPage.tsx:181` 均裸 `<img>`（【源码已证实】HIGH）。这些位置若渲染空/失效 URL，既无空 src 防护、也无破图兜底，与全站"统一走 `Image`"的约定相悖。
- 重构建议：统一用 `Image` 替换裸 `<img>`（尤其 `s.thumbnail`、`it.coverUrl` 这类后端字段可能为空的场景），或至少加空值保护。
- 证据等级：【源码已证实】；置信度：**HIGH**。

### C8 · 其它硬编码契约（认证 / OSS 预签名 / 分页游标 / 代理发现）
- **C8.1 会话 cookie（httpOnly sid）+ `credentials:'include'`**：所有 `apiFetch` 强制 `credentials:'include'` 携带后端 `set-cookie` 的 sid（api.ts:28）；`authStore` 注释明确会话为 httpOnly cookie。重构若改鉴权方案（如改 Bearer token），需同步所有 fetch 调用——而 `genericClient` 走的是 `Authorization: Bearer ${apiKey}`（直连服务商，不同机制），两套鉴权并存，勿混淆。【源码已证实】HIGH。
- **C8.2 OSS 直传预签名字段**：`apiSignOssUpload` 约定返回 `{success, objectKey, putUrl, getUrl, putExpires, expires, providerType}`（api.ts:251-275）；`useOssConfig`/`OssConfigPanel` 直接消费 `putUrl`/`getUrl`/`objectKey`。后端签名逻辑（`server.js` 的 `buildOssGetUrl`/`buildOssPutUrl`）字段名改变即破。【源码已证实】HIGH。
- **C8.3 监控游标分页**：`apiGetGenerations/apiGetAssets/apiGetIssues` 用 `before=ISO` 游标（`nextCursor`），前端 `MonitorPage` 等依赖 `nextCursor` 判是否有下一页（api.ts:1256-1286）。后端游标语义（`< created_at`）改变即破。【源码已证实】MEDIUM。
- **C8.4 后端自动发现**：`ensureApi()` 默认 `http://<hostname>:3001` + `GET /api/token`（api.ts:41-66）。前端 dev/build 都隐式依赖"后端必在 3001"。若部署改端口/路径，前端自动发现失败 → 全站降级到"内置默认数据（不持久化）"，表现成"登录/生成/素材全部失效但不报错"。【源码已证实】HIGH。
- **C8.5 充值订单状态枚举**：`RechargeOrder.status: 'pending'|'paid'|'failed'|'expired'`（api.ts:747），前端 `RechargePage` 轮询 `apiGetRechargeOrderStatus` 按 `paid` 切成功态。后端状态字面值改动即破。【源码已证实】MEDIUM。

### C9 · 构建期资源缺失（copyPublicDir:false 的副作用）
- 见 §1.5：生产构建 `dist/build2` 不含 `public/favicon.svg`、`public/icons.svg`、`public/samples/`，而 `index.html` 与部分代码按绝对路径 `/favicon.svg`、`/icons.svg`、`/samples/...` 引用 → **生产环境 favicon 缺失、samples 静态资源 404**。dev 模式因 Vite 仍服务 `public/` 而掩盖。重构部署流水线必须显式处理（开启 copyPublicDir 或迁移资源到 `src`）。
- 证据等级：【源码已证实】（vite.config.ts + index.html + public 目录存在）；置信度：**HIGH**。

## 3. React 19 特性注意（ref 即 prop，勿用 forwardRef）

- React 19 起 **`ref` 已是普通 prop**，组件可直接声明 `ref` 参数，`React.forwardRef` 已废弃（仍可用但不推荐）。
- **已存在误用**：
  - `src/components/ui/image.tsx:96`：`export const Image = React.forwardRef<HTMLImageElement, ImageProps>(...)`。
  - `src/components/ui/card.tsx`：`Card`/`CardHeader`/`CardTitle`/`CardDescription`/`CardContent`/`CardFooter` 全部 `React.forwardRef`（card.tsx:5/20/32/47/59/67）。
- **现状影响**：`forwardRef` 在 React 19.2 下**仍可运行**（非崩溃错误），所以属"技术债/反模式"而非阻断 bug。但重构时应注意：
  - 新写组件**不要再** `forwardRef`，直接把 `ref` 当 prop 收。
  - 若未来升级到彻底移除 `forwardRef` 的 React 版本，这两处需改写（且 image.tsx 内部已把 `ref` 透传到原生 `<img ref={ref}>`，改 prop 形态时逻辑保持一致即可）。
- 证据等级：【源码已证实】；置信度：**HIGH**（非阻断，标记 MEDIUM 风险）。

## 4. 与重构相关的技术债

1. **`tsc` 宽松 ≠ vite/esbuild 严格（已踩坑）**：`tsconfig.app.json` 继承 `@lark-apaas/coding-presets-react` preset，`tsc -p tsconfig.app.json`（即 `npm run typecheck`）的严格度与 esbuild/vite 实际转译并不等价。历史已出现"tsc 过、vite 构建/运行期才暴露类型或解析问题"的坑。重构时**不能只以 `tsc` 绿为安全线**，须 `vite build` 实际验证（本审计未运行构建以遵守"只读"，但此为已知风险）。【文档记载/推断】MEDIUM。
2. **多轮 Edit 同文件导致 import 重复 / ParseError**：`GenerationBar.tsx` 体积达 ~122KB（全仓最大组件），多次增量编辑易在同一文件堆积重复 `import` 或重复声明，触发 ParseError。重构应优先**拆分 `GenerationBar`**（生成状态机/余额校验/UI 三段），既是可读性也是稳定性需求。【源码已证实（文件体量与结构）】MEDIUM。
3. **API 入口物理分散**：`api.ts` 末尾从 `@/pages/Admin/UsersPage` 再导出购物车/订单类函数（`apiAddToCart/apiGetCart/apiGetOrders/...`）。即"服务层逻辑"写在页面文件里，违背分层。重构应把购物车/订单 API 与类型移入 `services/` 或 `@shared`，消除 `services→pages` 的反向依赖。【源码已证实】MEDIUM。
4. **静默 catch 兜底普遍**：`api.ts` 绝大多数函数 `catch { return [] / {} / null }`，业务失败被吞。重构若引入更严格的错误边界/可观测性，需先决定"哪些失败必须上抛"（如生成失败、扣费失败）而非一律静默。【源码已证实】MEDIUM。
5. **`genericClient` 直连服务商通道**与 `/api` 代理通道并存，两套字段抽取约定（OpenAI 默认 `data[].url` vs 自定义 `imageFieldPath` JSONPath）。重构做"生成抽象"时须保留这两种协议分支，勿一刀切。【源码已证实】LOW。

## 5. 审计发现摘要（最关键耦合 / 风险）

1. **【P0·C6】`canceled`(后端,单l) vs `cancelled`(前端,双l) 拼写不一致** —— 用户取消生成后，SSE 与轮询兜底均因状态字符串不匹配而不结算，卡片在最长 95 分钟内卡在"生成中"，取消功能在 UI 层近乎失效。前后端双向取证，HIGH。与 11 号文档联动，建议重构首发修复。
2. **【P0·C1/C2/C3】错误以"字符串+状态码"当协议** —— `apiFetch` 抛 `API <status>: <text>`，前端用正则/`includes('409')`/`/402|积分不足/` 反解 `code` 与业务分支；后端改任一文案/状态码/code 字面量即静默破坏余额不足、取消失败、注册冲突等核心流程。HIGH。
3. **【P1·C4】`SNAKE_MAP` 是隐性的前后端字段契约** —— 后端蛇形→驼峰映射表缺口会让前端驼峰字段 `undefined` 假死；前端无转换层、全信任后端。重构须让 `SNAKE_MAP` 与 `@shared` 契约类型单一真相对齐。HIGH。
4. **【P1·C7/C9】资源渲染与构建约定** —— 多处裸 `<img>` 绕过 `Image` 的空 src/破图兜底（尤其 `SamplesPage` 的 `s.thumbnail` 重演 #576 整页重载）；`copyPublicDir:false` 致生产构建缺失 `public/` 静态资源（favicon/samples）。HIGH。
5. **【P2·C5/§3】SSE 无名事件 + React19 forwardRef 反模式** —— SSE 依赖默认 `message` 事件与 `TaskUpdate` 字段形状，且 `useGenerationStream` 的 3s 轮询兜底不可移除；`image.tsx`/`card.tsx` 仍用 `forwardRef`（React19 已废弃，非阻断但属技术债）。HIGH/MEDIUM。

> 结论基调：**前端对后端的耦合高度依赖"隐式文本/状态码/字段命名契约"而非结构化协议**。重构若要安全，优先做三件事：(a) 把 `status` 取值与错误 `code` 收敛为 `@shared` 共享枚举/类型；(b) 统一 `canceled` 拼写；(c) 用 `@shared` 契约类型反向校验后端 `SNAKE_MAP` 与前端 `data/*.ts` 字段对齐。
