## 1. 认证流程

### 1.1 登录 / 注册流程
- **注册** `POST /api/auth/register`（网关前公开，源码 `server.js:1592` → `handleRegister` `server.js:1356`）：
  - 写入 `users(id, email, display_name, password_hash, reward_credits, role)`，密码用 `scrypt` 加盐哈希（`auth.cjs:27-41`）。
  - 默认 `role='user'`，赠送 `reward_credits`（默认 50，可由 `SIGNUP_BONUS_CREDITS` 覆盖）。
  - 注册成功后 `session.signSession({ id, role:'user' })` 并 `setCookie(res, 'sid', ...)`（`server.js:1385-1387`）。
- **登录** `POST /api/auth/login`（公开，`server.js:1593` → `handleLogin` `server.js:1390`）：
  - 校验 `verifyPassword`（`auth.cjs:32-41`，`timingSafeEqual` 防时序），成功后签发 `sid` cookie（`server.js:1409-1413`）。
  - 登录失败有速率限制 `rl:login:<ip>` 10 次/60s（`server.js:1392`）；登录失败封禁规则在 `server.js:744`。
- **刷新 / 登出**：`POST /api/auth/refresh`、`POST /api/auth/logout`（`server.js:1594-1595, 1417-1428`），均重新签发/清空 `sid`。
- **当前用户**：`GET /api/auth/me`（`server.js:1684` → `handleMe` `server.js:1430`）从 **cookie** 取身份（`session.getUserFromCookie`），不受 Bearer 令牌污染。

### 1.2 JWT 签发与校验位置
- **签发**：`auth.cjs:44-51 signSession()`，HMAC-SHA256（HS256），载荷 `{ sub, role, iat, exp }`，`exp = now + 7天`（`ACCESS_TTL_SEC = 7*24*3600`，`auth.cjs:11`）。
- **校验**：`auth.cjs:52-69 verifySession()`，常量时间比较，过期即拒；`getUserFromCookie(req)` 解析 `sid` cookie（`auth.cjs:93-96`）。
- **密钥来源**：`auth.cjs:9` `const SECRET = process.env.JWT_SECRET || 'dev-only-change-me';`
  - 【配置文件已证实·HIGH】当前 `E:/code/.env` 仅含 `PG_*`、`REDIS_*`、`PAYMENT_MASTER_KEY`，**不含 `JWT_SECRET`**，亦不含 `NODE_ENV`。
  - 【源码已证实·HIGH】因此 `SECRET` 回退为已知常量 `'dev-only-change-me'`，任意人可离线伪造任意 `sub`/`role`（含 `role:'admin'`）的合法会话 JWT。
  - 【源码已证实·HIGH】生产自检仅 `console.warn`（`server.js:3714-3716`），**不 fail-closed**，伪造令牌在生产仍可用（除非部署方另行注入 `JWT_SECRET`）。

### 1.3 API_TOKEN 机制（用途 / 是否可冒充系统或管理员）
- **生成**：启动期读取 `TOKEN_FILE`，缺失则 `crypto.randomBytes(24).toString('hex')` 并落盘（`server.js:23-29`）。
- **启用开关**：`devTokenEnabled = !isProduction || tokenFromEnv`（`server.js:31`）。`isProduction = NODE_ENV==='production'`；当前 `.env` 无 `NODE_ENV` → `isProduction=false` → **`devTokenEnabled=true`**。
- **系统身份注入**：`appGateway(req)`（`server.js:1274-1283`）——
  ```js
  if (devTokenEnabled && req.headers['authorization'] === `Bearer ${API_TOKEN}`) {
    req.user = { id: '__system__', role: 'system' }; return true;
  }
  const u = session.getUserFromCookie(req);          // 否则退回 cookie 会话
  if (u) { req.user = u; return true; }
  ```
  - 【源码已证实·HIGH】**Bearer 令牌优先于 cookie**：只要请求带 `Authorization: Bearer <API_TOKEN>` 且 `devTokenEnabled`，`req.user` 被强制置为 `system`，cookie 会话被忽略。
- **前端自动取用**：`src/services/api.ts:41-66 ensureApi()` 在首次调用时 `GET /api/token` 取回 token 并作为 `Authorization: Bearer` 注入**每一个**后续请求（`api.ts:17-22 headers()`）。即前端把“系统令牌”当作通用 Bearer 使用。

### 1.4 `/api/token` 端点（核心暴露面）
- 【源码已证实·HIGH】`server.js:3623` 位于 `http.createServer` 最外层、**早于任何鉴权网关**：
  ```js
  if (req.url === '/api/token' && req.method === 'GET')
    return sendJSON(res, 200, { token: API_TOKEN });
  ```
  - 完全无鉴权，任何人可 `GET /api/token` 取回当前 `API_TOKEN`。
  - 在 `devTokenEnabled=true`（当前运行实例即此状态）时，该 token 即“系统令牌”，配合 `appGateway` 的 Bearer 优先逻辑即获得 `role:'system'`。
- **冒充管理员链路**：`requireAdmin(req)`（`admin.cjs:19-20`）判定 `role==='admin' || role==='system'`。故持 `API_TOKEN` 者经 `appGateway` 得到 `system` → 通过**所有** `requireAdmin` 检查 → 等价于管理员（见 §4 P0）。

### 1.5 令牌存储与过期
- 会话令牌存 `sid` cookie（`HttpOnly; SameSite=Lax`，生产加 `Secure`）（`auth.cjs:83-87`）。
- 前端注释称“浏览器本地不落盘”（`api.ts:1-3`），`ensureApi` 内存缓存 token，未写 `localStorage`。
- 过期：会话 7 天（`auth.cjs:11`）；`API_TOKEN` 无过期、落盘持久（`server.js:27`）。
- 【源码已证实·HIGH】CSRF 缓解：`SameSite=Lax` 拦截跨站 `POST`（`auth.cjs:86`），故传统 CSRF 风险较低（正向）。

## 3. RBAC 现状

- 【源码已证实·HIGH】角色仅两档：`role TEXT NOT NULL DEFAULT 'user'`，取值 `'user'` / `'admin'`（`server.js:264`）。`users` 表无子角色/权限位/作用域字段。
- `system` 并非 `users` 表角色，而是 `appGateway` 在检测到 `API_TOKEN` Bearer 时临时注入的虚拟身份（`server.js:1277`）。
- **admin-only 端点（全部经 `requireAdmin`，`admin.cjs:19-20`）**，汇总如下：
  - 用户管理：`GET /api/admin/users`、`POST /api/admin/users/:id/credits`、`POST /api/admin/users/:id/status`、`PUT /api/admin/users/:id/role`、`DELETE /api/admin/users/:id`（`admin.cjs:597-625`）
  - 账务/对账：`GET /api/admin/transactions`、`GET/POST /api/admin/finance/*`、`GET /api/admin/ledger/*`（`admin.cjs:626, 1703, 1709-1726`）
  - 智能体与规则：`/api/admin/agents*`、`/api/admin/agent-providers*`、`/api/admin/agent-rules*`（含 toggle）（`admin.cjs:629-657`）
  - 参考样式审核：`/api/admin/reference-styles*`（review/promote）（`server.js:1728-1736`）
  - 模型/成本：`GET /api/admin/model-price-history`（`server.js:1739`）、`/api/admin/agents` 等
  - 运营/监控：`/api/admin/samples*`、`/api/admin/generations`、`/api/admin/assets`、`/api/admin/issues`、`/api/admin/audit`、`/api/admin/errors*`、`/api/admin/monitor/*`、`/api/admin/logs/*`、`/api/admin/console/stream`、`/api/oss/logs/*`（多处 `requireAdmin`）
  - 技能/市集后台：`/api/admin/skills*`（已先于通用 admin 分发，`server.js:1705`）
- 【源码已证实·HIGH】**注意**：`requireAdmin` 同时放行 `role==='system'`，因此上面所有 admin 端点对持有 `API_TOKEN` 者同样开放（见 §4 P0）。
- 无“只读管理员/财务管理员/运营”等子角色；admin 为全权。无基于资源的细粒度授权（如“只能看自己工作室”之外无更多维度）。

## 4. 安全缺口

### ⛔ P0-A `/api/token` 公开返回 API_TOKEN → 任意人可冒充系统/管理员
- **描述**：`server.js:3623` 在鉴权网关之前无条件返回 `API_TOKEN`；前端 `api.ts:41-66` 也依赖此端点。当前 `.env` 无 `NODE_ENV` → `devTokenEnabled=true` → 该 token 即“系统令牌”。攻击者只需 `GET /api/token` → 用 `Authorization: Bearer <token>` 调任意 `/api/admin/*` → `appGateway` 置 `system` → `requireAdmin` 放行 → **完全管理员接管**（读全量用户/积分、改角色、手动充值、删用户、看账务、清错误日志等）。
- **证据等级**：【源码已证实】+【配置文件已证实】；**置信度：HIGH**。
- **风险等级**：P0（远程未授权提权/全量数据泄露）。

### ⛔ P0-B 会话 JWT 密钥回退为公开默认值 → 可伪造任意身份会话
- **描述**：`auth.cjs:9` `SECRET = process.env.JWT_SECRET || 'dev-only-change-me'`。当前 `.env` 未设置 `JWT_SECRET`（`E:/code/.env` 已读，仅 PG/REDIS/PAYMENT 三项）。攻击者可本地用常量 `'dev-only-change-me'` 签发 `sid` cookie，payload 任意设 `sub` 与 `role:'admin'` → 以任意用户/管理员身份通过 `getUserFromCookie` → 绕过 `appGateway` cookie 分支。
- **证据等级**：【源码已证实】+【配置文件已证实】；**置信度：HIGH**（前提：部署未通过启动环境变量另行注入 `JWT_SECRET`；`.env` 未含，但无法 100% 排除启动脚本额外传参，故对“线上实际是否注入”标 MEDIUM，对“代码回退逻辑成立”标 HIGH）。
- **风险等级**：P0（会话伪造/认证绕过）。

### ⚠️ P1-C `DELETE /api/characters/:id` 缺 owner/role 校验（越权操作全局共享资源）
- **描述**：`server.js:2196-2207`：`DELETE` 仅校验 `if (!realUser) return 401`，随后 `DELETE FROM characters WHERE id=$1`。`characters` 表**无 `user_id`**（全局角色库，`server.js:2159` 注释“全员共享的创作预设”）。因此**任意登录用户**可删除他人/系统创建的任意角色预设，无需 admin。语义上属“越权操作共享资源”（非典型跨用户数据访问 IDOR，但授权模型缺失）。`POST /api/characters`（`server.js:2170`）同样任意登录用户可写入全局预设。
- **证据等级**：【源码已证实】；**置信度：HIGH**。
- **风险等级**：P1（数据完整性/越权写）。

### ⚠️ P1-D `appGateway` Bearer 优先于 cookie → 系统身份遮蔽真实会话，破坏审计归属与自保护
- **描述**：`server.js:1276-1278` 中只要带 `Bearer API_TOKEN` 即置 `req.user=system`，**忽略** cookie。前端 `api.ts` 每个请求都带此 Bearer，故正常登录用户的所有请求在后端 `req.user` 均为 `system`：
  1. 后台操作审计 `actorId = req.user.id = '__system__'`（`admin.cjs:594`），真实管理员操作被记为“系统”，**审计溯源失真**。
  2. 管理员自保护 `if (decodeURIComponent(m[1]) === actorId) return 400 '不能操作自己'`（`admin.cjs:608,615,622`）因 `actorId==='__system__'` 而**失效**——管理员可删除/禁用自己账号（自锁）。
  3. 依赖 `req.user`（而非 `realUser`）做授权的任何未来端点将被静默提权为 system。
- **证据等级**：【源码已证实】；**置信度：HIGH**。
- **风险等级**：P1（审计失真 + 自保护失效 + 设计脆弱性）。

### ⚠️ P2-E 内部“系统调用”账务 scope 标注与设计铁律不符（计费准确性，非鉴权）
- **描述**：`accounting.cjs:55-58` `recordConsumption` 的 `scope` 由调用方传入，**模块内无鉴权**。设计铁律（`accounting.cjs:3,48,53`）要求“系统自身调用大模型计为 `scope='system'`，客户收费=0”。但平台自用的提示词优化/翻译智能体记账为 `scope:'user', actorId: realUser.id`（`server.js:2763, 2908`），即平台自身 LLM 成本被计入用户 scope。属财务/对账准确性偏差，不直接构成越权，但会使 `/api/admin/ledger/summary` 盈亏口径失真。
- **证据等级**：【源码已证实】；**置信度：MEDIUM**（需结合 `customerChargeCredits` 取值确认是否双重计费，未在本次范围深挖）。
- **风险等级**：P2（计费准确性 / 合规）。

### ⚠️ P2-F `setup/init` 公开但 fails-closed，默认管理员密码硬编码于 `.env.example`
- **描述**：`/api/setup/init` 公开（`server.js:1618`），首个管理员建好后即锁定（409）。但 `.env.example:25` 给出 `ADMIN_SEED_PASSWORD=Admin@123456` 默认弱密码；生产自检仅 `console.warn`（`server.js:3717-3719`）不阻断。若部署未覆盖，存在弱口令风险。
- **证据等级**：【源码已证实】+【文档记载但源码未证实】（默认值是否实际用于运行实例未知）；**置信度：MEDIUM**。
- **风险等级**：P2（若为公开部署且未改密）。

### ℹ️ 其他已核对的“未越权”点（正向，供重构基线）
- `DELETE/PUT /api/media/:id`：`DELETE FROM media WHERE id=$1 AND user_id=$2`（`server.js:2085`）；PUT 校验 `owner!==realUser.id && role!=='admin'` 拒绝（`server.js:2104`）；字段白名单禁止改 `user_id`（`server.js:2107`）→ 防 IDOR 偷素材。✅
- `studio/projects` 全量 `owner_id=$2` 过滤（`server.js:2268,2300,2313`）。✅
- `dispatcher.cancelTask` 校验 `row.user_id !== userId` 拒绝跨用户取消（`dispatcher.cjs:1234`）；`listActiveTasks` 按 `userId` 过滤（`dispatcher.cjs:1050`）。✅
- `reference-styles` 删除校验 `user_id!==user.id && role!=='admin'`（`reference-styles.cjs:139`）；且 `currentUser()` 显式排除 `__system__`（`reference-styles.cjs:19`），设计上比其它模块更严谨。✅
- 会话 cookie `HttpOnly; SameSite=Lax`（生产 `Secure`）→ CSRF 风险低（`auth.cjs:86`）。✅

## 6. 审计发现摘要（按 P0/P1 排序）

1. **[P0] `/api/token` 无鉴权公开返回系统令牌**（当前 `devTokenEnabled=true`）→ 远程攻击者取令牌即获 `system` 身份，绕过全部 `requireAdmin`，等同管理员接管全站（用户/积分/账务/删除/日志）。**最高优先级修复**：移除公开返回、改为仅启动时打印/环境变量注入、并对 system 令牌与 admin 路由解耦。
2. **[P0] 会话 JWT 密钥回退公开常量 `'dev-only-change-me'`**（`.env` 未设 `JWT_SECRET`）→ 可离线伪造任意 `role:'admin'` 会话，完全认证绕过。**必须**在生产注入强随机 `JWT_SECRET` 并 fail-closed（缺失即拒绝启动）。
3. **[P1] `DELETE /api/characters/:id`（及 `POST`）缺 owner/role 校验** → 任意登录用户可删/写全局共享角色预设，应限制为 admin-only 或加归属字段。
4. **[P1] `appGateway` Bearer 优先于 cookie** → 系统身份遮蔽真实会话，导致审计 `actorId` 恒为 `__system__`、管理员“不能操作自己”自保护失效、未来端点静默提权。应让 `req.user` 反映真实 cookie 身份，system 令牌仅用于明确的内部通道。
5. **[P2] 内部系统调用 `scope` 标注不符账务铁律 + 默认 admin 弱口令仅告警** → 账务口径失真与潜在弱口令，建议在重构期一并收紧（账务 scope 归一 + 强制改密/禁止默认口令上线）。

> 备注：本审计未修改任何源码、配置、数据库；只读依据为 `server/`、`src/` 源码与 `.env` 文件。运行时实际是否通过启动参数注入了 `JWT_SECRET`/`NODE_ENV=production` 无法从文件确证，相关项置信度已在表中标注。
