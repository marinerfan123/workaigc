## 2. AES-256-GCM 与 PAYMENT_MASTER_KEY【源码已证实】
- `const ALGO='aes-256-gcm'`(crypto.cjs:12)；`IV_LEN=12`(13)。
- `getKey()` 读 `process.env.PAYMENT_MASTER_KEY`(16)，要求 **32 字节=64 hex**，否则抛错(17-24)。
- `encrypt`(27-34)→`iv.ct.tag` 三段 hex；`decrypt`(36-46)→`createDecipheriv+setAuthTag+final`。
- **密钥错误时 fail-closed 成立（GCM 认证标签保证）**：
  - 缺失 → getKey 抛 → loader 跳过该 provider → 下单 503。
  - 长度不对 → 抛 → 同上。
  - 值错误（≠seed 时密钥）→ `decipher.final()` 认证失败抛异常 → 同上跳过 → 503（**不会解密成乱码静默通过**）。
- ⚠️ 低危 fail-OPEN 后门：`decrypt` 中 `if(parts.length!==3) return stored`(39-40) → 若 DB 字段为非规范无点明文则原样返回（正常 encrypt 恒为 3 段，故正常数据不受影响；仅当 DB 被写入无点明文时才触发，需 DB 写权限）。

## 3. 创建订单流程【源码已证实】
- 入口 `createOrder`(payments.cjs:59-175)，路由 `POST /api/credits/orders`(248)。
- **sign 生成**：`hmac('sha256', SIGN_SECRET, `${payOrderNo}:${amount}:${channel}`)`(138)；`SIGN_SECRET=PAYMENT_MASTER_KEY||PAYMENT_SIGN_SECRET||''`(11)。**此 sign 仅是本地订单完整性标记，不构成入账凭证**；入账必须过 webhook 验签(文件头注释:10)。
- 入库：`INSERT recharge_orders(... pay_order_no, sign, expired_at, bonus, package_id)`(141-145)，状态固定 `'pending'`。
- 金额/bonus 取自 `topup_packages`(73-83)，后端权威。

**"无 provider → 503" 成立（payments.cjs:100-101）**：`providerEntry=await loader.getDefault().catch(()=>null)`；`if(!providerEntry) return sendJSON(res,503,...)`. 且 `loadPaymentSettings()` 缺/异常返 null→503(93)；全局开关关→503(94-97)。**无任何 DEV/模拟回退分支**(注释:4)。

## 6. ★ 发现的真实缺口（资料库未记载，需重构决策）
- **缺口 A：过期订单仍可被迟到回调入账**【源码已证实】。`webhook.cjs:110` 仅短路 `status==='paid'`，**不处理 `status==='expired'`**。order-expiry 把 pending→expired(41-51)，但 webhook 对 expired 订单：金额校验通过→插 webhook_events→置 paid→加余额。**不会双入账**（幂等索引保证），但"过期≠终态"——这是与"expired=已死"直觉相悖的取舍，是否符合重构后预期**待产品确认**（多数场景"用户真付款就该到账"其实正确，但应显式记录）。
- **缺口 B（低危 TOCTOU）**：`webhook.cjs:136-139` 余额 `UPDATE ... RETURNING credits` 后**未校验 rowCount**。极端竞态下（FK CASCADE 删用户致订单同步删）可能余额 0 行更新但 credit_transactions 仍以 balance_after=null 插入 → 账本有 grant 而余额未增。**建议补 `if(bal.rowCount===0) throw`**。

## 7. 余额增加与流水（重要：webhook 绕过 billing）【源码已证实】
- 入账事务(webhook.cjs:128-168，单事务)：
  1. 订单置 paid(129-134)
  2. **本金入账（直接裸 SQL，非 billing）**：`UPDATE users SET recharge_credits=recharge_credits+$1 ... RETURNING credits`(136-139)
  3. 写 `credit_transactions(kind='grant',pool='recharge',ref=o.id,balance_after)`(141-145)
  4. **bonus 赠送**：仅当 `o.bonus>0`(147)，再次 UPDATE recharge_credits+=bonus(150-153) + 第二条 credit_transactions(ref=`${o.id}:bonus`)(156-160) → **bonus 与本金同入 recharge 池**
  5. payment_audit('paid')(162-166)；COMMIT(168)
- `users.credits` 是 STORED 生成列，recharge 变更自动反映到总额。
- **与 billing.cjs 关系**：webhook **完全未引用 billing**（Grep 证实；仅 shop/dispatcher/server 用 billing）。这是实现差异——webhook 自行保证幂等（靠 webhook_events 唯一索引），未复用 billing 的双池/幂等键逻辑。**重构应统一或显式记录**，避免两套记账语义漂移。

## 8. order-expiry worker【源码已证实】
- `createOrderExpiryWorker`(order-expiry.cjs:16-96)；`start()` 起 `setInterval(tick,60000)`+启动即扫一次(78-85)；`timer.unref()`(82) 不阻止进程退出。
- 过期标记：单条原子 UPDATE(41-51)，双分支兼容（老订单 expired_at NULL 按 created_at 阈值；新订单按绝对时刻）。
- 阈值取 `payment_settings.default_expires_min`(33-34)，缺省 15 分钟。
- **pending 泄漏风险分析**：下单不预留积分（积分仅 webhook 成功时入账）→ 过期无需释放；与 webhook 的 FOR UPDATE 行锁天然串行 → **pending 不会泄漏成已付**（但见缺口 A：expired 仍可被迟到真实支付入账）。

## 9. 安全验证：当前 PAYMENT_MASTER_KEY 能否解密凭据（不打印明文）【未知·待核验】
- 解密成功充要条件（逻辑推导自 crypto.cjs:15-46）：①密钥存在且长度==64 hex；②其值 == seed 时所用密钥（GCM 认证标签保证）。
- 同源证据：server.js:3 `import 'dotenv/config'` 与 seed-easypay.cjs:8 均加载**同一 .env**；二者均读 `process.env.PAYMENT_MASTER_KEY`。
- **逻辑结论**：若 server 与 seed 共用同一 .env（强证据指向是）→ 密钥一致、解密成功、provider 正常加载；若运行时 .env 与 seed 时不同（密钥轮换未重跑 seed）→ GCM 解密抛异常 → provider 全部跳过 → 下单 503（fail-closed，不会用错密钥静默通过）。
- **无法从静态代码确认**：实际密钥值是否匹配、DB 当前行是否确为 encrypt 产物——需运行时/DB 实测（本侦察只读、不打印密钥，标【未知·待核验】）。建议受控环境用 `decrypt` 比对 `maskSecret` 输出，或观察下单是否 503。
